# P34 — ray2026constrainttax
Verification level: V4 · Read depth: full · Read on: 2026-09-20 · PDF: 11_PAPERS/pdfs/2026_Ray_ConstraintTax.pdf
Bibliographic: The Constraint Tax: Measuring Validity-Correctness Tradeoffs in Structured Outputs for Small Language Models; Jaideep Ray (no affiliation printed; jaray@acm.org); 2026; arXiv:2605.26128v1 [cs.LG] 20 May 2026; 8 pages incl. Appendix A. No venue stated.

## Problem
Deployed LLM applications pass model completions directly into software (JSON envelopes, typed traces, regex-limited fields, tool-call arguments) (Abstract p.1). "Structured outputs are now a serving contract" and "product code often treats parseability as the gate before execution" (§1 p.1). For sub-3B on-device small language models (SLMs), a hard schema competes with the task for limited decoding capacity, so "the wrapper can change the answer" (Abstract p.1). "A valid JSON object can still encode the wrong decision, so a dashboard that tracks parse success alone can improve while downstream execution gets worse" (§1 p.1). The concerning case "is not merely invalid JSON; it is wrong answer, valid schema" (§2.1 p.2).

## Research question(s)
Stated as a measurement question (§1 p.1): "when a small model is forced into a schema, how much semantic correctness is lost relative to comparable unconstrained or prompt-only baselines?" Five contributions listed (§1 p.1): (1) define constraint tax; (2) separate schema validity, answer accuracy, executable accuracy, trace correctness, latency, token count, structural overhead, wrong-valid-schema rate; (3) low-compute harness (MLX + vLLM/SGLang); (4) measure a silent executable-correctness regression in a calendar tool-call analogue; (5) the "reason free, constrain late" design pattern.

## Method / architecture / algorithm
- Framing (§2.1 p.2, Eq. 1): Q = f(R_reason, R_format, B_decode) — quality depends on reasoning resources, formatting resources, decoding budget. Constrained decoding is treated as "a reasoning intervention", and the structured-output path is treated "as a full system" (model + prompt + decoding algorithm + schema + validation stack) (§2.2 p.2).
- Harness (Fig. 1 p.3): deterministic task generator → prompt + mode (freeform/regex/schema) → backend router (MLX, HF, vLLM, SGLang) → generation → parser + validator + executor + trace check → records (tax, validity, latency).
- Tasks (§3.1, Table 1 p.3, "StructReason-Small"): five deterministic synthetic families — arithmetic_two_step, symbolic_string, object_tracking, boolean_logic, tool_call_argument — with ground truth stored as final answer string plus typed trace steps. Separate production analogue: calendar tool-call object task (Appendix A p.8 gives exact prompt, JSON Schema with `additionalProperties: false`, regex patterns for date/time, `duration_minutes` integer ≥ 1, and executable checker code).
- Output modes (§3.2, Table 2 p.3): freeform, freeform_direct, freeform_brief_reasoning, prompt_json (JSON requested only by prompt), final_only_regex, answer_only_schema (minimal answer JSON schema, hard constrained decoding), rationale_answer_schema, typed_trace_schema, delayed_constraint (reason first, package answer second).
- Constraint tax (§4.2 p.3, Eq. 2–3): Tax(m,t,c;b) = max(0, Acc(m,t,b) − Acc(m,t,c)); normalized form divides by max(ε, Acc(m,t,b)). Clipping at zero intentional; gains reported as gains.
- Error taxonomy (§4.4 p.3): correct_valid, invalid_json, parse_failure_freeform, schema_validation_error, trace_answer_contradiction, wrong_answer_valid_schema.
- Protocol (§5 pp.3–4): Main GPU run — vLLM, each checkpoint × 1,000 instances × 5 families × 5 modes (freeform, freeform_direct, freeform_brief_reasoning, prompt_json, answer_only_schema) = 15,000 generations. Production analogue — one checkpoint on calendar tool-call task, 200 examples per directly generated mode, plus derived delayed-packaging control that re-serializes prompt-json first-stage records. Backend replication — answer_only_schema across vLLM and SGLang. 3B boundary — prompt_json vs answer_only_schema. Local expanded-interface study — MLX, four public small models, 20 examples per family, full interface set.
- Statistics (§4.3 p.3): paired deltas on same instances; nonparametric bootstrap 95% CIs over problem instances, reported only where present in artifacts.
- Design pattern (§6.6 p.6): "reason free, constrain late" — let the model solve, then project the result into the executable object.

## Dataset(s) (+ size, licence) / benchmark
Synthetic deterministic generator ("StructReason-Small", Table 1 p.3): main run 1,000 instances × 5 families per checkpoint (600 generations per mode per family row in Table 4 p.5, aggregated across sub-3B checkpoints); calendar analogue 200 examples per mode (Table 6 p.5); expanded study 20 examples per family (§5 p.4). Licence: Not reported. All numbers "come from generated JSONL or CSV artifacts in the experiment directories" (§5 p.3).

## Baselines
Baseline interface b = prompt-only JSON (prompt_json) or freeform for the same model and instances (§4.2 p.3). Models (Tables 5, 8, 9 pp.5–6): Qwen2.5-0.5B, Qwen2.5-1.5B, SmolLM2-1.7B (main sub-3B suite); Qwen2.5-3B-Instruct (boundary); Qwen2.5-1.5B-Instruct (calendar analogue). Expanded-interface study: "four public small models" (names not given in text, §5 p.4). Serving engines: vLLM, SGLang, MLX, HF Transformers (§3.3 p.2).

## Metrics
(§4.1 pp.2–3) Schema validity; Answer correctness (normalized answer = ground truth); Executable accuracy (task-specific checker accepts object); Trace correctness; **Wrong-valid-schema rate** (schema-valid but fails answer/executable checker); Structural overhead, latency, tokens. Derived: constraint tax (answer tax, exec tax), validity delta, wrong-valid delta (Table 5 p.5).

## Key results (each with table/figure/page reference)
- Table 3 p.4 / Fig. 2 p.4 (main-suite aggregate, sub-3B, 95% bootstrap CI): prompt_json — Answer acc 19.7 [18.3, 21.1]%, Schema valid 61.5 [59.7, 63.3]%, Exec acc 12.0 [10.9, 13.2]%, Wrong-valid-schema 49.5 [47.7, 51.2]%; answer_only_schema — 11.0 [9.9, 12.2]%, 100.0 [99.9, 100.0]%, 11.0 [9.9, 12.2]%, 88.9 [87.8, 90.0]%; Delta −8.7 pts, +38.5 pts, −1.0 pts, +39.4 pts. Text §6.1 p.4: "The parser sees a cleaner stream; the executor sees more well-formed objects carrying wrong content."
- Table 4 p.5 (per family, 600 generations/mode): answer tax largest for arithmetic_two_step (26.8 pts; prompt 32.2% → schema 5.3%) and object_tracking (12.5); boolean_logic 3.5; symbolic_string 0.5; tool_call_argument 0.0 (both 0.0% answer acc). Wrong-valid delta: +65.0, +21.3, +13.8, +60.5, +36.7 respectively. Boolean logic "is the counterpattern: validity improves without an executable-accuracy loss" (§6.1 p.4).
- Table 5 p.5 (tax by model): Qwen2.5-0.5B answer tax 11.9, exec tax 6.1, validity +45.7, wrong-valid +51.8; Qwen2.5-1.5B 20.0, 12.6, +16.6, +29.2 ("largest main-suite tax"); SmolLM2-1.7B 0.0, 0.0, +53.2, +37.4 ("constraint is an accuracy gain"); Qwen2.5-1.5B calendar: exec tax 43.5 [36.0, 51.0], validity +0.0, wrong-valid +43.5; Qwen2.5-3B boundary: 15.3 [11.2, 19.2] answer/exec tax, validity +16.3 [13.9, 18.7], wrong-valid +31.6 [27.7, 35.2].
- Table 6 p.5 / Fig. 3 p.5 (calendar tool-call, Qwen2.5-1.5B-Instruct, n=200/mode): tool_call_prompt_json — Exec acc 91.5 [87.5, 95.0]%, Schema valid 100.0%, Wrong-valid 8.5 [5.0, 12.5]%, Latency 1.63 s; tool_call_delayed_packaging — 91.5%, 100.0%, 8.5%, 1.63 s + pkg.; tool_call_schema — 48.0 [41.0, 55.0]%, 100.0%, 52.0 [45.0, 58.5]%, 1.69 s; Schema − prompt: −43.5 pts [−51.0, −36.0], +0.0 pts, +43.5 pts [35.5, 51.0], +0.06 s.
- Table 7 p.5 (calendar failure taxonomy, 200/mode): prompt_json and delayed_packaging — Correct 183, Wrong duration 8, Wrong topic 7, Multi-field 2; tool_call_schema — Correct 96, Wrong duration 102, Wrong topic 0, Multi-field 2. Text p.5: "102 of 104 hard-schema failures are single-field duration errors." Example (§6.3 p.5, Fig. 4): request for 30-minute meeting → constrained decoder emits `duration_minutes: 180`; "A calendar API would accept the object and schedule the wrong meeting."
- Table 8 p.6 (backend replication, answer_only_schema answer acc): Qwen2.5-0.5B 2.7% vLLM / 2.7% SGLang; Qwen2.5-1.5B 11.7 / 11.7; SmolLM2-1.7B 18.7 / 25.7 (backend-sensitive). SGLang required an RMSNorm compatibility patch (§6.4 p.5).
- Table 9 p.6 (Qwen2.5-3B boundary): prompt_json Answer 39.0 [36.2, 42.0]%, Schema valid 82.6 [80.2, 85.0]%, Wrong-valid 43.6%; answer_only_schema 23.7 [21.1, 26.3]%, 98.9 [98.2, 99.5]%, 75.2%; Delta −15.3 [−19.2, −11.2], +16.3 [13.9, 18.7], +31.6 [27.7, 35.2]. "The evidence does not support the claim that this issue is limited to the smallest models" (§6.5 p.6).
- Table 10 p.6 / Fig. 5 p.6 (MLX expanded-interface, 4 models, answer/valid/exec): prompt_json 31.5 / 70.0 / 24.5; answer_only_schema 26.8 / 99.0 / 26.8; rationale_answer_schema 36.5 / 97.8 / 36.5; delayed_constraint 40.7 / 100.0 / 40.7.
- Negative results (§7.3 p.7): SmolLM2 improved under direct schema; rationale-bearing schemas and delayed constraints improved executable accuracy; some constrained-serving attempts failed until patch.
- Deployment recommendations (§7.5 p.7): (1) measure prompt-only JSON before hard-constraining; (2) track wrong-valid-schema rate as first-class reliability metric; (3) prefer final-answer or delayed constraints when reasoning needed; (4) replicate constrained modes on intended serving backend; (5) "Treat schema validity as an interface SLO, not as a task-success metric."

## Stated limitations (with location)
§9 p.7: deterministic setup "a strength for measurement and a limit for generalization"; synthetic families are stress tests, "not a replacement for broad user workloads"; calendar task "still a controlled analogue rather than logged agent traffic"; expanded-interface study uses fewer examples and is "design evidence"; delayed constraints should be replicated on deployment serving engines; "The study also does not establish a scaling law"; model coverage "intentionally limited to low-compute, locally accessible, or commodity-GPU-feasible checkpoints"; structured-output implementations change quickly. §4.3 p.3: MLX expanded-interface study is "design evidence rather than the primary significance claim". §3.3 p.2: latency comparisons only meaningful within backend families.

## Limitations we observe (labelled OURS)
- OURS: Single-author preprint without institutional affiliation; no peer review stated; no code/data repository URL in the PDF despite references to "experiment directories" (§5 p.3).
- OURS: Only sub-3B models (plus a 3B boundary); no evidence about the constraint tax at frontier or mid-size model scales, which are what most web applications call.
- OURS: Latency reported only for the calendar task (Table 6 p.5, +0.06 s) and not for the validator/executor layer itself; "structural overhead" and token counts are defined (§4.1 p.3) but no numeric table for them appears in the paper.
- OURS: The wrong-valid-schema failures are concentrated in one integer field (`duration_minutes`, Table 7 p.5) — per-field-type breakdown across string/date/enum/pattern fields is not given, though the schema (Appendix A.2 p.8) contains regex-patterned date/time fields whose error rates are not separately reported.
- OURS: "Semantic" correctness here means exact-match to a deterministic oracle (answer or executable checker); no human or LLM-judge evaluation, and no notion of domain-invalid-but-plausible values beyond the checker.
- OURS: Four expanded-study models are not named in the text; results in Table 10 cannot be attributed to specific checkpoints.

## Future work stated
§9 p.7: "larger models and additional model families are needed to determine when, or whether, this effect disappears"; "Delayed constraints should be replicated on the serving engines used in deployment before being treated as the default." §7.3 p.6: benchmark reports should pin checkpoint, tokenizer, decoding engine, schema, hardware, serving-engine patches.

## Relevance to our RQs (RQ1 structural-pass-but-semantic-fail; RQ2 frequency by field type; RQ3 LLM vs random/rule/human inputs; RQ4 violation types; RQ5 semantic layer detection; RQ6 latency/overhead; RQ7 trade-off)
- RQ1: DIRECT. Defines and measures the "wrong-valid-schema rate": 88.9% of hard-schema outputs in the main suite (Table 3 p.4) and 52.0% in the calendar tool-call task (Table 6 p.5) are schema-valid but wrong.
- RQ2: PARTIAL. Per-task-family breakdown (Table 4 p.5) and per-field failure counts for the calendar object (Table 7 p.5: duration vs topic vs multi-field) — closest published evidence that a specific integer field dominates schema-valid errors; no general field-type taxonomy.
- RQ3: NONE for random/rule/human inputs; compares decoding interfaces for the same LLM only.
- RQ4: PARTIAL. Error taxonomy (§4.4 p.3) distinguishes invalid_json, schema_validation_error, wrong_answer_valid_schema, trace_answer_contradiction; calendar taxonomy (Table 7) gives wrong duration / wrong topic / multi-field.
- RQ5: PARTIAL. Executable checker (Appendix A.3 p.8) is the semantic layer; its detection rate is by construction 100% on the oracle, so no detection-performance evaluation.
- RQ6: PARTIAL. Only one latency comparison (Table 6 p.5: constrained decoding +0.06 s over prompt-only, 1.63 s → 1.69 s); no overhead figure for the validation/checker layer.
- RQ7: DIRECT. The whole paper is a validity-vs-correctness trade-off measurement (constraint tax, Eq. 2–3 p.3; Table 5 p.5); cost is in accuracy, not latency/money.
