## Problem
Automated test generation for web forms is "sparsely explored" (§1 p.1); generating suitable values "necessitates a grasp of the context of each input field: understanding the semantics of fields, as well as how they relate to one another" (§1 p.1). Forms are human-centric, DOM structure can obscure semantics, and LLMs applied naively hit context-size limits and miss cross-field constraints (§2 p.3: GPT-4 token-limit error on the Air Canada form; larger-context GPT-4 "could only handle validations within single input fields").

## Research question(s)
§4 p.8: RQ1 "How effective is FormNexus in generating tests for forms?"; RQ2 "How does FormNexus compare to other techniques?"; RQ3 "What is the contribution of FormNexus's components towards the end results?"

## Method / architecture / algorithm
FormNexus, an "LLM-agnostic" pipeline (§1 p.1):
1. Form Entity Relation Graph (FERG) (§3.1 p.4–5): for non-container DOM nodes, concatenate ADA text embeddings with node2vec structural embeddings (Fig. 2 p.4); connect visually adjacent elements with cosine-similarity edge weights (graph G=(V,E,W), §3.1.2 p.4); prune: auxiliary node (label/hint/feedback) keeps only its highest-similarity edge to an input; text-to-text edges kept only above μ + λσ with λ = 1/2 (§3.1.2 p.5). Cross-field relevance InputFieldSim = max{sim(label1,label2), sim(input1,input2)} (§3.1.3 p.5).
2. Constraint generation (§3.2.1 p.5–6): per-field prompt (Fig. 4 p.6) with Time Context, Form Context (title/description/labels), Input Field HTML + local context, Global Context (related fields); LLM selects from a fixed list of constraint templates (Table 2 p.6; 14 types in total, adapted from Jest assertions, §3.4 p.8) plus a freeTextConstraint for logic not expressible as templates (§3.2.1 p.6). Example (Listing 1 p.6): From 1 → toBeTruthy, toBeAlphabetical, toHaveLengthCondition('>',2), not.toBeEqual('To 1'), not.toBeEqual('From 2').
3. Value generation (Fig. 5 p.6): LLM produces values complying with constraints; already-assigned related-field values are substituted into cross-field constraints (§3.2.1 p.6–7).
4. Feedback loop (§3.2.2 p.7): fill and submit; detect outcome by DOM diff before/after submission filtered by keywords "not valid, required, denied, and similar terms"; connect inline feedback to fields via FERG; unattached feedback treated as global; regenerate constraints with feedback in the prompt; repeat until a successful submission.
5. Constraint validation (§3.2.3 p.7–8): negate one constraint at a time (Listing 2 p.7), resubmit; success ⇒ constraint was not enforced by developers (recorded as a discrepancy/test); failure ⇒ constraint confirmed.
6. Test generation (§3.3 p.8): every recorded (values, outcome) pair becomes a Selenium end-to-end test: navigate, populate, submit, assert expected submission state.
Implementation in Python; GPT-4 or Llama 2; temperature 0 for all experiments (§3.4 p.8; §4 p.8).
Core coverage concept: Form Submission State (FSS) — Definition 1 §2 p.2: a tuple S=(I,F) with I the minimal input subset that causally determines feedback F; all FSSs disjoint. Air Canada form has 20 FSSs (§2 p.2; Table 1 p.3).

## Dataset(s) (+ size, licence) / benchmark
Newly curated dataset (contribution 3, §1 p.2): 30 web forms, 102 input fields, 1–14 inputs per form, avg 3.4 (§4.2 p.9). Categories (Table 3 p.9): Travel 8 forms/31 inputs; Query 13/17; Registration 4/24; Data Entry 5/30. Sources: popular US websites from Mind2Web [18] plus open-source applications (6 forms, 37 inputs) for tasks like user creation (§4.2 p.8–9). Selection criteria: domain range, form-type diversity, "presence of input value validation", no authentication required (§4.2 p.8). Focus on free-form inputs (text, number, date), not checkboxes/dropdowns (§4.2 p.9). Ground-truth FSSs established manually by the authors via a 4-step procedure (baseline valid values → isolated single-input mutation with predetermined rules → combinatorial variation → consolidation) (§4.1 p.8). Licence: Not reported. Ground truth released with the repository (§8 p.12).

## Baselines
(§4.3 p.9) (a) Static module: pre-defined values chosen by the field's type attribute, incl. extremes (very large/small numbers, zero); (b) Crawljax [35] random value generation, 20 values per input field; (c) standalone GPT-4 prompted with the form's HTML to generate successful and erroneous inputs; (d) standalone Llama 2, same; (e) QTypist-like: GPT-4 with QTypist's linguistic patterns (original QTypist not reproducible: Curie fine-tuning unavailable, dataset undisclosed). Santiago et al. [41] excluded (no replication package); Auto-GPT tried but "unable to generate form input values" (footnote 1, p.9).

## Metrics
- FSS coverage (% of manually established FSSs covered by generated tests) (§4.4 p.9).
- Form passing rate = rate of successful FSSs, i.e., proportion of forms for which a successful submission was generated ("equivalent to the form-filling task", §1 p.2; §4.5 p.10).
- Ablation reports Average FSS Coverage and Total Passing Rate (Table 4 p.10).
- Secondary descriptive stats: constraints per field, % invalidated, iterations to stable constraints (§4.4 p.9).

## Key results (each with table/figure/page reference)
- FSS coverage (Fig. 6 p.9; §4.4–4.5 p.9): FormNexus-GPT-4 89%; FormNexus-Llama 2 51%; standalone GPT-4 71%; standalone Llama 2 35%; static 57%; Crawljax 30%. → "25% improvement in FSS coverage over the next best-performing baseline, namely standalone GPT-4" (§4.5 p.9).
- Passing rate (Fig. 7 p.10; §4.5 p.10): FormNexus-GPT-4 83%; GPT-4 63%; QTypist 57%; Llama 2 33%; FormNexus-Llama 2 30%; static 23%; Crawljax 3%. Baselines' "generated values often deviated from the forms' specific requirements, limiting their success to only forms with simple validation rules" (§4.5 p.10).
- Standalone GPT-4 produced no viable values for 3/30 forms (2 context-size, 1 nonsensical); Llama 2 for 14/30 (46%) due to context size (§4.5 p.9–10).
- Constraint statistics (§4.4 p.9): FormNexus-GPT-4 averaged 3.77 constraints/field, 389 total (~13.0/form), ~26% invalidated in validation; stable constraints within 1.13 iterations on average (second iteration needed in 4/30; never more than two). FormNexus-Llama 2: 13.11 constraints/field, 1,359 total, ~76% invalidated.
- Ablation (Table 4 p.10): No FERG 82% coverage / 70% passing; No Date 83% / 70%; No Feedback 87% / 73%; No Form Context 88% / 83%; full 89% / 83%. FERG adds 7 pp coverage (paper says "9% improvement", relative) and +13 pp passing (§4.6 p.10). Date context helps forms with date fields by ~20% vs 7% overall (§4.6 p.10). Feedback loop adds ~2% on the cases needing >1 iteration (§4.6 p.10).
- By category (§5 p.11): travel forms — FormNexus-GPT-4 82% vs GPT-4 42% vs QTypist 36%; query forms — 92% / 91% / 90% (little validation, so little difference).
- Motivating example (§2 p.3): on the Air Canada 20-FSS form, QTypist covered 3/20 (15%); large-context GPT-4 6/20 (30%) and "could only handle validations within single input fields"; a few-shot example of same-city origin/destination produced that one case but "failed to generalize to broader geographical or date-related constraint scenarios".

## Stated limitations (with location)
§5 "Limitations" p.11: (1) insufficiently detailed application feedback hinders constraint inference; (2) does not model dynamic application state (e.g., repeated user creation would error); (3) complex regular expressions or intricate mathematical inter-field relationships "may prove challenging for LLMs to process directly" — suggests specialized solvers; (4) LLM hallucinations, notably in constraint naming (mitigation: similarity mapping to the predefined list). Threats to validity (§5 p.11): subject representativeness; manually populated ground truth may not reflect actual form logic.

## Limitations we observe (labelled OURS)
- OURS: Validity oracle is the form's own observable feedback (keyword-filtered DOM diff); inputs that are accepted by the form but semantically wrong for the domain would count as "success" — the paper does not measure semantic correctness independent of the application's validation.
- OURS: Success-outcome detection relies on keyword heuristics ("not valid, required, denied"); false positives/negatives of this detector are not quantified.
- OURS: Only 30 forms / 102 inputs; single run at temperature 0; no variance, seeds, or statistical tests reported; "significantly" used without tests.
- OURS: No latency, token, or cost figures for the feedback loop; no timing per form.
- OURS: The ~26% of GPT-4-inferred constraints that the application did not actually enforce is a measure of LLM over-inference, but the converse (constraints the form enforces that the LLM never inferred) is only indirectly captured through uncovered FSSs.
- OURS: PDF is the arXiv v2 with placeholder DOI; alignment with the ISSTA 2024 camera-ready is unverified.

## Future work stated
§7 p.11–12: expand the dataset; support multi-step web forms; investigate Graph-Neural-Network-based embeddings for FERG. §5 p.11: integrate specialized solvers for complex regex/mathematical constraints.

## Relevance to our RQs (RQ1 structural-pass-but-semantic-fail; RQ2 frequency by field type; RQ3 LLM vs random/rule/human inputs; RQ4 violation types; RQ5 semantic layer detection; RQ6 latency/overhead; RQ7 trade-off)
- RQ1: Partial evidence. Standalone LLM values reach a successful submission on only 63% (GPT-4) / 33% (Llama 2) of forms (Fig. 7 p.10), and the motivating study shows GPT-4 handling single-field format validation but failing cross-field semantic constraints (same origin/destination, date order) (§2 p.3). The paper does not separate "format-valid but rejected" from "format-invalid" failures, so a structural-pass/semantic-fail rate cannot be extracted directly.
- RQ2: Category-level, not field-type-level: travel forms (cross-field constraints) 42% GPT-4 coverage vs query forms 91% (§5 p.11); date fields singled out as a common validation site (§4.6 p.10). Per-field-type (email/phone/date/number) failure frequencies: Not reported.
- RQ3: Yes — directly compares LLM (GPT-4, Llama 2, QTypist-style) vs random (Crawljax) vs rule-based (static type-based) inputs on the same 30 forms: passing rates 63% / 33% / 57% vs 3% vs 23% (Fig. 7 p.10); coverage 71% / 35% vs 30% vs 57% (Fig. 6 p.9). No human-written input group.
- RQ4: Implicit taxonomy via constraint templates (Table 2 p.6: equality, length, alphabetical, whitespace, …; 14 types) and FSS examples (Table 1 p.3: required/format for origin; invalid date format; same origin & destination; repeated origin across legs; return before departure).
- RQ5: The LLM infers semantic constraints from field context and the form's feedback validates them; there is no independent semantic-validation layer for incoming inputs — the application's own validation is the oracle.
- RQ6: Only iteration counts (1.13 avg to stable constraints, §4.4 p.9); no latency/overhead.
- RQ7: Not addressed.

## Potential gap / novelty evidence (quote LOCATION, e.g. "§5.2 p.7: authors state X"; short quotes only, ≤ 25 words)
- §2 p.3: large-context GPT-4 "could only handle validations within single input fields" — evidence that LLM-generated inputs satisfy per-field format checks but miss cross-field semantic constraints.
- §4.5 p.10: baseline values "often deviated from the forms' specific requirements, limiting their success to only forms with simple validation rules".
- §4.4 p.9: "approximately 26% of these constraints were invalidated on average" — LLM-inferred constraints over-approximate the application's real validation logic.
- §5 p.11: complex regex / "intricate mathematical relationships between input fields … may prove challenging for LLMs to process directly".
- §1 p.1: "the realm of form test generation remains sparsely explored [41]".
- Gap for us: the paper's goal is test generation and coverage; it does not measure how often LLM-produced inputs pass syntactic validation yet violate semantic constraints, nor evaluate a runtime semantic-validation layer or its overhead.

## Terminology the paper uses for structural-vs-semantic validity (and how it defines a "valid" input)
- Uses "valid and invalid input combinations" (§2 p.2) and "passing and failing values" (§4.3 p.9); does not use the words "syntactic" or "structural" validity.
- "Semantic" refers to the meaning/context of fields and their inter-relations ("semantics of fields, as well as how they relate to one another", §1 p.1; "semantic constraints of most of the input fields", §4.6 p.10).
- Distinguishes format-type validation ("inputs that conform to particular formats", FSS 2–3, §2 p.3) from "more complex scenarios" — geographic constraints (From ≠ To; consecutive trips) and temporal ordering (return after departure; not in the past) (§2 p.3).
- Constraints described as "literal, and extrapolated from localized data such as labels" (per-field) vs constraints that "depend on values drawn from different fields" (cross-field) (§3.2.1 p.6).
- Operational validity: Definition 2 (§3.2.2 p.7): "A Failure in submission is identified by the reception of error feedback from the web application … a Successful submission is denoted by the absence of such failure feedback and the transition to the intended outcome of the form." A valid input set is therefore one the application accepts; validity is defined by application behaviour, not by an external semantic criterion.
