## Problem
Prompt injection is the top OWASP LLM risk; existing defences (input filters, system-prompt hardening, output monitoring) each operate at a single pipeline stage: "input filters cannot inspect retrieved documents; privilege enforcement cannot catch injections that the model chooses to follow ...; and output monitors have no capacity to prevent an injection from reaching the model" (Sec. 1, p.2). RAG chatbots remain exposed to indirect injection via poisoned knowledge-base documents (Abstract, p.1).

## Research question(s)
No numbered RQs. Contributions (Sec. 1, p.2): (1) formal threat model for direct/indirect injection in RAG chatbots; (2) model-agnostic three-layer defence deployable as middleware; (3) controlled evaluation on 5,080 samples across three models; (4) ablation and error analysis.

## Method / architecture / algorithm
Three layers plus a cross-cutting audit loop (Fig. 4, p.8; Fig. 8, p.12):
- **Layer 1 Input Screening** (Sec. 4.2, p.8): (a) rule-based pattern library — regex / keyword-proximity rules over a normalised input (Unicode folding, whitespace collapsing, Base64/URL decoding); three categories: instruction override, role hijacking, prompt extraction (Table 4, p.8); disposition = pass-with-flag / sanitize / block. (b) "Semantic Anomaly Detection": a lightweight classifier on the sentence embedding of the user input (sentence-transformers/all-MiniLM-L6-v2 fine-tuned for binary injection classification; AdamW, lr 2e-5, batch 32, early stopping on validation F1) outputting injection probability s1 ∈ [0,1]; inputs with s1 > τ1 are flagged and forwarded with score as metadata (Sec. 4.2.2, p.8; Sec. 5.1.3, p.12; Fig. 5, p.9).
- **Layer 2 Privilege-Constrained Context Assembly** (Sec. 4.3, p.9): three provenance tiers (Operator [SYS], Retrieval [RET], User [USR]) with tagging + meta-instruction; a chunk scanner applies a reduced Layer-1 library to retrieved chunks (remove or [FLAGGED]) (Table 5, p.9; Fig. 6, p.10).
- **Layer 3 Output Auditing** (Sec. 4.4, p.10): policy rule engine (Table 6: system-prompt cosine similarity ≥ θsp = 0.85; role-token detection; instruction-acknowledgment phrases; Llama Guard 2 harmful-content score ≥ τ3 = 0.5; propagated L1 flag) plus semantic drift detection (cosine distance between reference persona-compliant response embedding and live response; τdrift = 0.40) (Sec. 4.4.2, p.10; Sec. 5.1.4, p.12).
- **Audit loop** (Sec. 4.5, p.10): append-only structured logs, alerting thresholds, retraining of the classifier.

## Dataset(s) (+ size, licence) / benchmark
(Sec. 5.2, Table 7, p.13) 5,080 samples, 80/10/10 split: 2,840 adversarial (612 from PromptBench + BIPIA; 188 manually curated, Cohen's κ = 0.91 between two annotators; 1,440 GPT-4o paraphrase augmentations) across five categories (instruction override 740, role hijacking 620, prompt extraction 480, KB poisoning 520, retrieved-doc payload 480); 2,240 benign queries from MS-MARCO filtered to customer-support-relevant queries. Knowledge base: 500 public product-documentation/FAQ documents, dense retrieval + FAISS, top-3 chunks (Sec. 5.1.1, p.12; Sec. 6.2, p.18). Licences: Not reported in sections read.

## Baselines
(Sec. 5.4, p.14) Undefended; L1 Only; L2 Only; L3 Only; NeMo Guardrails (default prompt-injection protections) as a published single-layer guardrail baseline. Target models: GPT-4o (OpenAI API, temperature 0), Llama 3 8B Instruct and Mistral 7B Instruct (Hugging Face transformers on a single NVIDIA A100 40 GB GPU; temperature 0, top_p 1) (Sec. 5.1.2, p.12).

## Metrics
(Sec. 5.3, p.13–14) Attack Success Rate (ASR, Eq. 1; goal-achievement judged per goal: GPT-4o judge with 3-point rubric for IO, cosine similarity ≥ 0.85 to system prompt for DE, Llama Guard 2 for BM; κ vs human 0.87/0.94/0.91); False Positive Rate (FPR, Eq. 2: fraction of benign queries blocked or sanitised); Detection Rate (DR = complement of ASR); Response Quality Score (BERTScore F1 vs human reference). Latency: median and p95 per component (Sec. 5.7).

## Key results (each with table/figure/page reference)
- Macro-averaged ASR 71.4% (undefended) → 11.3% (full framework), −60.1 pp; L1 Only 44.2, L2 Only 51.8, L3 Only 38.6, NeMo Guardrails 35.1 (Table 8, p.14).
- FPR: undefended 0.0, L1 5.1, L2 1.3, L3 6.7, NeMo 8.4, **full framework 4.8%** (Table 8, p.14; Table 9, p.15). Full-framework FPR is lower than L1+L3 (6.9%) and L2+L3 (7.4%) because L2 reduces injections reaching L3 (Sec. 5.6, p.15; Sec. 6.1, p.17).
- RQS 0.89 across all defended conditions vs 0.91 undefended (Table 8, p.14).
- ROC: Layer 1 semantic classifier AUC 0.941 (operating point FPR 0.051, TPR 0.722); Layer 3 harmful-content predicate AUC 0.923 (FPR 0.067, TPR 0.702) (Sec. 5.5.3, p.14; Fig. 10, p.16).
- **Latency (Table 10, p.15, "on an NVIDIA A100 40 GB GPU. LLM inference time is excluded")**: median / p95 in ms — L1 Pattern Matching 2.1 / 4.3; L1 Semantic Classifier 18.4 / 27.6 (L1 subtotal 20.5); L2 Chunk Scanner 9.7 / 16.2; L2 Context Assembly 1.8 / 3.1 (L2 subtotal 11.5); L3 Policy Rule Engine 11.3 / 19.8; L3 Semantic Drift Check 17.9 / 26.4 (L3 subtotal 29.2); **Framework Total median 61.2 ms, p95 97.4 ms**. Measured "from receipt of the user input to delivery of the response, averaged over 500 benign queries per model on the local deployment hardware" under single-request conditions (Sec. 5.7, p.15; Sec. 6.2, p.18). Per model (Fig. 11, p.16): Mistral-7B 60.4 ms, Llama-3 8B 59.7 ms, GPT-4o 65.3 ms; the two semantic encoding steps (L1 classifier + L3 drift) ≈ 60% of overhead; all under a 100 ms budget.
- Rule engine alone: "high precision on known attacks at near-zero latency" (2.1 ms median), the embedding classifier "extends recall to unseen phrasings at a modest computational cost" (Sec. 4.2.2, p.8; Table 10).
- Residual bypasses (Table 11, p.16; n = 32): novel phrasing evading L1 37.5%; implicit instructions bypassing L2 scanner 25.0%; persona drift below τdrift 21.9%; multi-turn accumulation 15.6%.
- Per-goal (Fig. 9, p.15): full framework ASR ≈ 10.5–12.0 (IO), 6.0–7.5 (DE), 12.0–13.0 (BM) across the three models.

## Stated limitations (with location)
(Sec. 6.2, p.17–18) Static black-box attacker model — white-box adversary could craft evasions; single-turn evaluation (multi-turn bypass = 15.6% of residual cases); benign knowledge base of 500 product docs, not adversarially representative; threshold sensitivity — τ1, τ3, θsp, τdrift calibrated on a validation set from the same distribution as the test set; latency measured under single-request conditions on dedicated hardware, concurrent load may raise p95 beyond 97.4 ms. Also Sec. 4.3.2 (p.9): Layer 2 depends on the model's instruction-following.

## Limitations we observe (labelled OURS)
- OURS: "Semantic" in this paper means embedding-based *adversarial-intent* classification of prompts, not validation of whether a data value is semantically valid for a form field/business rule. The layered rules+classifier architecture and the latency accounting are transferable; the task is not.
- OURS: FPR is defined on benign natural-language queries (MS-MARCO), not on structurally valid but semantically wrong data inputs; no field-typed inputs exist in the dataset.
- OURS: The 61.2 ms figure excludes LLM inference and includes Layer 2/3 costs that a pure input-validation layer would not incur; the input-side cost alone is the L1 subtotal (20.5 ms median), of which 18.4 ms is the MiniLM classifier.
- OURS: Data/code availability statement says "available at: GitHub Repository" with no URL in the PDF text or link annotations (p.20) — reproducibility not verifiable. Conflict of interest declared (Sparkverse AI affiliation, p.20). Journal metadata fields on p.1 are template placeholders.

## Terminology the paper uses for structural-vs-semantic validity
- "rule-based pattern library" / "pattern-based detection" / "signature" (structural, surface-level) vs "semantic anomaly detection" / "semantic classifier" / "semantic anomaly classifier" (embedding-based intent) (Sec. 4.2, p.8).
- "semantic drift detection" (output persona drift, Sec. 4.4.2, p.10); "semantically novel phrasings" (bypass class, Sec. 5.8, p.16).
- "structural defenses" is used for the whole framework in contrast to model capability ("Model capability does not substitute for structural defense", Sec. 6.1, p.17) — i.e. "structural" here means architectural, not syntactic.
- Does not use "structural validation", "schema validation", or "semantic validation" of data.
