## Problem
Automated test-case generation for web forms is hard because "due to the complex, multi-level structure of web pages, it can be difficult to automatically capture their inherent contextual information" (Abstract p.1). "Contextual information" is defined as "the structure and attributes of web-form elements — derived from web-form HTML — such as their tags, types, and attributes (e.g., name, id), as well as the relationships among these elements" (§1 p.2). Prior LLM work (Alian et al. [1]) covered only two LLMs within one framework; "no comparative study examining different LLMs has yet been reported for web-form-test generation" (Abstract p.1; §1 p.3).

## Research question(s)
§4.1 p.14: RQ1 "How effective are the web-form tests generated by different LLMs?" — RQ1.1 prompt types; RQ1.2 LLM comparison. RQ2 "What is the quality of the generated web-form tests?" — RQ2.1 "Why are some generated web-form tests not successfully submitted?"; RQ2.2 quality from testers' perspective (online user study).

## Method / architecture / algorithm
Five-step framework (Fig. 3 p.7): (1) HTML pruning — Algorithm 1 p.8 keeps only attributes in S = {id, name, type, placeholder, src, disabled, readonly, value, checked, required, selected} and drops others (e.g., class, data-id, user-role) (§3.1 p.8–9, Listings 2–3 p.9). (2) Context construction, three variants (§3.2 p.9–10): Raw HTML (pruned HTML string); LLM-Processed HTML (LLM converts pruned HTML to JSON, then natural-language sentences, Algorithm 2 p.10); Parser-Processed HTML (Jsoup converts HTML to JSON deterministically, §3.2.3 p.10). (3) Prompt design (§3.3 p.11; Fig. 4 p.12): global prompt (app name, form title, element count), task prompt (RH-P / LH-P / PH-P; asks for "valid/reasonable values based on the specific attributes of each element, such as placeholders or input types"), note prompt ("Avoid including a step-by-step analysis"), instruction prompt (output array of jQuery selector=value pairs between triple backticks), objective prompt. (4) LLM communication via a unified API wrapper, outputs stored in MySQL with metadata (§3.4 p.12). (5) Web-form-test insertion: Selenium findElement(By.cssSelector) + sendKeys (Listing 4 p.14), click submit, then "a monitor is set to wait until the submission triggers a response from the application server: If a response is caught, then it is considered a successful submission; otherwise, it has failed" (§3.5 p.14).
LLM settings: default hyperparameters (e.g., OpenAI temperature 1, top_p 1) (§4.2 p.15). Each form run three times per LLM per prompt type (§4.3 p.16). Environment: MacBook Pro M3 Max, 64 GB; Java test script; Chrome 122.0.6261.112; ChromeDriver 122.0.6261.128 (§4.4 p.17). LLM access via paid APIs and free student/new-user quotas (§4.5 p.17).

## Dataset(s) (+ size, licence) / benchmark
30 open-source Java web applications from GitHub (from 300 identified via keywords "Java web", "Jobs", "Books"; excluded those without forms or not runnable) with 146 web forms (§4.3 p.15). Forms manually classified by three product managers (open coding) into five categories (§4.3 p.15–16; Fig. 6 p.16): Authentication 31.51%, Profile 14.38%, Content Management 43.15%, Search 2.74%, Transaction 8.22%. 11 LLMs (Table 1 p.15): GPT-3.5 (gpt-3.5-turbo), GPT-4, GLM-3, GLM-4, GLM-4V, Baichuan2-53B, LLaMa2-7B/13B/70B (via replicate.com), Spark-3, Spark-3.5. 146 × 11 × 3 prompts × 3 runs = 14,454 generated tests; 438 test tasks per LLM per prompt (§4.3 p.16; Table 2 p.17). Licences of the 30 applications: Not reported. Dataset, code, results: https://github.com/abelli1024/web-form-test-gen-empirical-study (§1 p.4).

## Baselines
None external. The study compares LLMs against each other and prompt types against each other. Explicitly: "we did not include other baseline methods (such as random-based approaches [5, 83]) in our comparison" (§5.4 p.28). Alian et al. (FormNexus) is discussed as prior work, not run (§1 p.3; §6.1 p.29–30).

## Metrics
- Successfully-submitted rate (SSR): "the proportion of LLM-generated web-form tests that could be successfully inserted into the web forms and submitted. A higher SSR indicates that the generated test cases align better with the expected input and structural requirements of the web forms — the LLM has produced valid test cases" (§4.3 p.16). Footnote 5 p.16: "This metric was originally referred to as the 'form passing rate' [1]" (Alian et al.).
- Two-tailed Mann-Whitney U test (α = 0.05) and Vargha–Delaney Â12 effect size (Eq. 1, §4.3 p.16; Table 3 p.20).
- Failure-reason distribution over all failed submissions (§5.2.1 p.24–25).
- Tester quality score, 5-point Likert, 20 testers, Kendall's W for agreement (§4.3 p.16–17; §5.2.2 p.25–27).
Code coverage deliberately not used (§5.4 p.28).

## Key results (each with table/figure/page reference)
- Average SSR across all LLMs and prompts: 60.37% (Table 2 p.17). By prompt: RH-P 60.21%, LH-P 50.27%, PH-P 70.63% (Table 2 p.17; §5.1.1 p.18).
- Per-LLM average SSR (Table 2 p.17): GPT-4 98.48%; GLM-4 89.50%; Baichuan2 89.04%; Spark-3.5 83.18%; GLM-3 74.66%; GPT-3.5 65.60%; Spark-3 55.78%; LLaMa2-70B 54.11%; LLaMa2-13B 28.08%; LLaMa2-7B 25.65%; GLM-4V 0.00%. GPT-4 per prompt: RH-P 98.86% (433/438), LH-P 97.03%, PH-P 99.54% (436/438). LLaMa2-7B LH-P 0.23% (1/438); LLaMa2-13B LH-P 0.91%; LLaMa2-70B LH-P 6.62%.
- Abstract p.1: other LLMs' SSRs "decreased by 9.10% to 74.15%" vs GPT-4; §5.1.2 summary p.22 states "between 52% and 98% lower" (Â12-based) — two different framings in the same paper.
- Statistical comparison (Table 3 p.20; §5.1.2 p.21): GPT-4 significantly better than every other LLM under every prompt; GLM-4, Baichuan2, Spark-3.5 win 24, 23, 20 of 30 pairwise comparisons; LLaMa2-13B, LLaMa2-7B, GLM-4V fewest.
- SSR by form category (Table 4 p.22): GPT-4 ≥ 94.44% everywhere (RH-P Transaction lowest 94.44%; LH-P Search 83.33%); GPT-3.5 RH-P Authentication only 27.54%; LLaMa2-7B RH-P Search 0.00%; with PH-P, GPT-4, Baichuan2, GLM-4, LLaMa2-70B, Spark-3.5 all reach 100% on Search forms.
- Failure analysis of 5,728 failed submissions (§5.2.1 p.24–25): Reason 1 — wrong output format required by the prompt (40.82%); Reason 2 — "unable to generate the correct web-form test content based on the provided contextual information" (29.50%), e.g., GLM-3 "#person=Number Person" for a number field (Table 6 p.24), Baichuan2 returning placeholder text as values ("#username=Your Email Address", Table 5 p.23); Reason 3 — API connection problems (29.68%).
- Some LLMs (LLaMa2-13B/70B, Baichuan2) with RH-P "only returned the hint texts (e.g., 'Please enter the user name'), without generating any web-form tests" (§5.1.1 p.19).
- Tester study (§5.2.2 p.25–27; Table 8 p.27): Kendall's W = 0.94; overall mean quality 2.47/5; GPT-4 3.62, GLM-4 3.31, Baichuan2 3.17, Spark-3.5 3.03, GLM-3 2.83, Spark-3 2.42, GPT-3.5 2.36, LLaMa2-70B 2.18, LLaMa2-13B 1.65, LLaMa2-7B 1.62, GLM-4V 1.00. Prompt means: RH-P 2.40, LH-P 2.26, PH-P 2.76. 11/20 testers already use LLMs in QA; 16/20 concerned about privacy/security (§5.3.2 p.27).
- Insights (§5.3 p.27–28): PH-P 20.36% more successful than LH-P and 9.94% more than RH-P; GPT-4 recommended; GLM-4/Baichuan2 "only about 10% less than GPT-4"; LLaMa2-70B if privacy constraints.

## Stated limitations (with location)
§5.4 Threats p.28–29: (1) representativeness of subjects; no random-based baselines included; (2) three prompt types only, each run three times; (3) SSR rather than code coverage; (4) only open-source apps — closed-source may differ; (5) uniform prompts may not suit every LLM; (6) validity of tests: "we focused on evaluating the correctness of submission statements when a web form receives a set of valid tests: If the AUT returned a successful response, then the submission was considered successful. However, some invalid data (such as 'user@' or '@email.com' — incomplete email addresses) may also be successfully submitted due to a lack of exception-handling processes" (p.29). §4.5 p.17: API access via free quotas may not reflect commercial costs. §7 p.32: "some web forms may lack essential exception-handling processes, which could allow invalid web-form tests to be successfully submitted."

## Limitations we observe (labelled OURS)
- OURS: The success oracle is "a response from the application server" being caught (§3.5 p.14), not an explicit success/error classification; a server response carrying a validation error could be counted as success. Combined with the authors' own admission that incomplete emails can be "successfully submitted", SSR measures structural acceptance, not semantic validity.
- OURS: No separation between "value rejected by client/server validation" and "LLM produced no usable value"; Reason 2 (29.50%) mixes format/type errors with placeholder-echo behaviour, and Reason 3 (29.68%) is infrastructure noise inflating failure counts.
- OURS: Default temperature 1 with three repeats; per-run variance is not reported.
- OURS: The 30 apps and 146 forms are all open-source Java; the paper reports no per-field-type (email/date/number/phone) failure rates despite Table 6/7 anecdotes.
- OURS: Human quality study shows LLM inputs only "Neutral" at best (max 3.71/5), even for GPT-4 with 99.54% SSR — a hint that high submission rate does not imply high input quality, but the paper does not analyse this discrepancy.
- OURS: No latency/cost measurements (acknowledged as future work §4.5 p.17).
- OURS: arXiv v2 read; TOSEM version unverified.

## Future work stated
§7 p.32: optimise prompts, fine-tune LLMs, model-specific prompt adaptation, RL-based prompt optimisation; build an automated multi-LLM web-form-test tool with coverage/bug-detection analysis, extend to dynamic content, multi-step workflows, mobile/desktop; "exploring how to generate effective invalid tests to detect these vulnerabilities" (XSS/SQLi) including APIs and dynamic pages; data-privacy vulnerability detection. §5.4 p.29: "The validation of such invalid tests will form part of our future work." §4.5 p.17: cost-effectiveness study.

## Relevance to our RQs (RQ1 structural-pass-but-semantic-fail; RQ2 frequency by field type; RQ3 LLM vs random/rule/human inputs; RQ4 violation types; RQ5 semantic layer detection; RQ6 latency/overhead; RQ7 trade-off)
- RQ1: Central. The paper's headline metric (SSR) is exactly "structural pass" and the authors concede semantically invalid inputs pass it (§5.4 p.29). GPT-4 reaches 99.54% SSR (Table 2 p.17) while testers rate its inputs only 3.62–3.71/5 (Table 8 p.27) — but the paper does not quantify the structural-pass/semantic-fail rate; that is our gap.
- RQ2: Category-level SSR only (Table 4 p.22); no per-field-type rates. Anecdotal field-type failures: number field ("Number Person"), datetime-local ("Select time"), select values (Table 6 p.24).
- RQ3: LLM-vs-LLM only (11 models); explicitly no random or rule-based baselines (§5.4 p.28); no human-written inputs — human testers only rate LLM outputs.
- RQ4: Failure taxonomy is about generation failures (format / content / connection, §5.2.1 p.24–25), not about semantic-violation types of submitted inputs.
- RQ5: No semantic validation layer; the application's own (often missing) validation is the only check.
- RQ6: Not measured; cost noted qualitatively (§4.5 p.17).
- RQ7: Not addressed; only a privacy-vs-effectiveness model-choice trade-off (Insight 5/7, §5.3 p.27–28).

## Potential gap / novelty evidence (quote LOCATION, e.g. "§5.2 p.7: authors state X"; short quotes only, ≤ 25 words)
- §5.4 p.29: "some invalid data (such as 'user@' or '@email.com' — incomplete email addresses) may also be successfully submitted due to a lack of exception-handling processes." — direct admission that SSR counts semantically invalid inputs as successes.
- §5.4 p.29: "The validation of such invalid tests will form part of our future work." — gap left open by the authors.
- §7 p.32: "some web forms may lack essential exception-handling processes, which could allow invalid web-form tests to be successfully submitted."
- §3.5 p.14: "If a response is caught, then it is considered a successful submission; otherwise, it has failed." — weak oracle; supports the need for a semantic check independent of the application.
- §4.3 p.16: SSR "indicates that the generated test cases align better with the expected input and structural requirements of the web forms" — validity defined structurally.
- §5.4 p.28: "we did not include other baseline methods (such as random-based approaches [5, 83])" — RQ3 comparison absent.
- Table 2 p.17 / Table 8 p.27: 98.48% average SSR vs 3.62/5 tester quality for GPT-4 — the divergence we want to measure.
- §1 p.3 & §6.4 p.31: "no comprehensive research has systematically evaluated multiple LLMs in the context of web-form testing" — their claimed novelty is breadth of LLMs, not validity semantics.

## Terminology the paper uses for structural-vs-semantic validity (and how it defines a "valid" input)
- "successfully-submitted rate (SSR)" — the operational validity measure; equated with "valid test cases" (§4.3 p.16) and with Alian et al.'s "form passing rate" (footnote 5 p.16).
- "contextual information" / "context" — structure and attributes of form elements and their relationships (§1 p.2; §3.2 p.9); a test is marked "●" when "the context of the web-form test was consistent with the web form" (§5.2.1 p.24).
- "valid/reasonable values" and "contextually relevant values" — prompt wording (Fig. 4 p.12).
- "valid and invalid tests": valid tests "guide normal execution and validate the program's functionality", invalid tests "test the program's ability to detect and handle exceptions" (§5.4 p.29).
- "syntactically precise" is used only for the LLM's output array format (§3.3.5 p.11), not for input-value validity.
- The paper never uses "semantic validity"; it does not distinguish structural (format/type) acceptance from semantic correctness, and acknowledges that its notion of success can be satisfied by invalid data (§5.4 p.29).
