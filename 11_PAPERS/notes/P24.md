## Problem
Black-box REST API testing tools driven by OpenAPI specifications "often fall short in complex scenarios, particularly when handling specific data formats or inter-parameter dependencies (IPDs)" (§2.2 p.4–5) and "often generate invalid API requests, without considering the parameter value formats and the IPDs" (§2.4 p.6). Specification-enhancement tools (NLP2REST, ARTE, RESTGPT) extract rules statically but "lack the ability to dynamically interact with testing tools during execution" and cannot refine inputs from server feedback (§1 p.2). RESTGPT costs ~$10 per specification and relies on a hosted model, raising cost and data-exposure concerns (§3.1 p.7).

## Research question(s)
§4 p.11: RQ1 — how do LlamaREST-EX / LlamaREST-IPD compare with RESTGPT in identifying IPDs and generating valid inputs; RQ2 — effect of fine-tuning and quantization on code/operation coverage; RQ3 — comparison with state-of-the-art REST testing tools on coverage; RQ4 — 500-error detection vs those tools; RQ5 — ablation of parameter-description analysis, server-response analysis, LlamaREST-IPD, LlamaREST-EX.

## Method / architecture / algorithm
Two fine-tuned Llama3-8B models (§1 p.2; §3 p.6–10; Fig. 2 p.7):
- LlamaREST-IPD: given parameter name + description (+ server response message at test time) outputs an IPD rule (Requires, Or, OnlyOne, AllOrNone, ZeroOrOne, Arithmetic/Relational/Complex — Martin-Lopez catalogue) in a structured form, e.g. "IF startTime THEN travelMode == 'driving'" (§3.3.1 p.8–9).
- LlamaREST-EX: given parameter name + description (+ server response) outputs a list of example values (§3.3.1 p.9).
- Training data (§3.2 p.7–8): IPD database from Martin-Lopez [47] filtered to exclude benchmark specs → 551 parameters with IPDs; rules generated by RESTGPT then manually validated (25/551 = 4.5% fixed, ~5 hours, one author). EX database from 4,133 APIs-guru specs (>1.8 M parameter sets), targeting parameters with enumerated values.
- Fine-tuning (§3.3.2 p.9): QLoRA on a 40 GB A100 (Colab), batch size 8, early stopping (35 epochs EX, 51 epochs IPD); Llama2-style tokens; separate models because a joint model showed catastrophic forgetting on IPD detection (§3.3.1 p.8).
- Quantization (§3.3.3 p.9–10): llama.cpp, 2-bit (2.96 GB), 4-bit (4.58 GB), 8-bit (7.95 GB).
- Testing loop (§3.4 p.10): integrated into ARAT-RL (Q-learning over operations/parameters, Eq. 1; ε-greedy). The Value Generator "produces parameter values, typically chosen randomly but in conformance with the expected types"; the two LMs are activated only "when repeated failures occur (e.g., multiple 4xx responses)", prompted with parameter description plus server response message; 2xx lowers Q-value, 4xx/500 raises it.

## Dataset(s) (+ size, licence) / benchmark
Benchmark: 12 real-world REST services (Table 1 p.11) — 9 open-source (Features-Service 1,688 LOC/18 ops; Genome-Nexus 22,143/23; Language-Tool 113,170/2; Market 7,945/13; Person-Controller 601/12; Project-Tracking-System 3,784/67; Rest-Countries 1,619/22; User-Management 2,805/22; YouTube(-Mock) 2,422/1) and 3 online (FDIC 6 ops; Ohsome 122 ops; Spotify 12 ops). Drawn from the ARAT-RL benchmark (10 services) plus RESTGPT study services; SCS, NCS (written by EvoMaster authors), OCVN (auth), OMDB (toy) excluded (§4.1 p.11–12). Ground truth for RQ1: RESTGPT's manually extracted rule dataset — value-constraint rules for 7 services, IPD rules for 3 services (§4.2 p.13). Fine-tuning data: 551 IPD parameters; 4,133 specs / >1.8 M parameter sets from APIs-guru (§3.2 p.7). Licences: Not reported.

## Baselines
RQ1: RESTGPT (ChatGPT-3.5 Turbo based; values from its artifact) and base Llama3-8B with RESTGPT's prompts (§4.2 p.13). RQ2: five LlamaRestTest configurations (base, FT, FT+8-bit, FT+4-bit, FT+2-bit). RQ3/RQ4: RESTler v9.2.4, EvoMaster v3.0.0, ARAT-RL v0.1, MoRest (from authors), all given RESTGPT-enhanced specifications (§4.1 p.11; §4.4 p.16). DeepREST and AutoRestTest noted as concurrent, not compared (§5 p.20).

## Metrics
- "Precision of semantically valid value generation": share of generated values judged semantically valid by two external developers independently, discrepancies resolved by consensus (§4.2 p.13; Table 3 p.12).
- Number of correct IPD rules generated out of 18 ground-truth rules (Table 4 p.12).
- Code coverage (method/branch/line via JaCoCo) for open-source services; operations successfully processed for closed-source services; unique 500 errors (ARAT-RL script, deduplicated by response message) (§4.1 p.12).
- Inference time per IPD extraction (§4.3 p.15). Setup: M1 MacBook Pro 64 GB, 1-hour budget per tool per service, 10 runs averaged (3 runs for ablation) (§4.1 p.11).

## Key results (each with table/figure/page reference)
- Semantically valid value generation (Table 3 p.12), averages over 7 services: LlamaREST-EX FT 72.44%; FT+8-bit 66.12%; FT+4-bit 60.21%; FT+2-bit 29.12%; RESTGPT 68.82%; base Llama3-8B 22.94% (text on p.13 says "24.94%" — internal inconsistency; Table 3 says 22.94%, abstract/§1 p.3 say 22.94%). Per service, base Llama3-8B: Spotify 0.00%, Ohsome 2.78%, Genome-Nexus 9.00%, FDIC 14.29%, YouTube 21.67%, REST-Countries 46.84%, Language-Tool 60.00%. LlamaREST-EX FT beats RESTGPT on Ohsome (92.16 vs 76.83) and Genome-Nexus (57.02 vs 36.25) but loses on Language-Tool (69.23 vs 82.98; e.g., output "en" instead of "en-GB") and FDIC (54.69 vs 70.42; domain-specific financial knowledge) (§4.2 p.13).
- IPD rules (Table 4 p.12): of 18 ground-truth rules, LlamaREST-IPD FT 12; FT+8-bit 7; FT+4-bit 6; FT+2-bit 1; RESTGPT 9; base Llama3-8B 2. Note: abstract/§1 say "12 out of the 17 dependencies" while Table 4's Total row says 18 — internal inconsistency.
- Coverage by configuration (§4.3 p.15; Fig. 3 p.14): base 49.21% method / 23.24% branch / 48.51% line; FT 50.11 / 23.55 / 49.91; FT+8-bit 55.8 / 28.3 / 55.3 (best); FT+4-bit 54.0 / 27.9 / 53.5; FT+2-bit 52.9 / 25.7 / 52.6. Operations processed on closed-source services (Table 5 p.14): base 23.0; FT 24.5; 2-bit 25.4; 4-bit 34.4; 8-bit 37.5 (Ohsome 11.2 → 24.5).
- Inference time per IPD (§4.3 p.15): FT 48.9 s; 8-bit 36.9 s; 4-bit 26.2 s; 2-bit 26.1 s. Quantized models "processing for instance 22–81% more inference tasks in the same time budget".
- Vs tools (§4.4 p.16–17; Fig. 4 p.16; Table 6 p.14): LlamaRestTest (8-bit) 55.8% method vs EvoMaster 45.8, ARAT-RL 41.7, MoRest 33.3, RESTler 33.1; branch 28.3% (+9.2 to +18.7 pp); line 55.3% (+10.0 to +22.1 pp); operations 37.5 vs 9.9–11.6 (Ohsome: 24.5 vs 0.0 for all others).
- 500 errors over 10 runs (Table 2 p.11): LlamaRestTest 204; ARAT-RL 160; MoRest 140; RESTler 130; EvoMaster 130. Only LlamaRestTest found errors on Ohsome (36) and Spotify (8) — Spotify case required generating valid 22-character playlist IDs (§4.5 p.17).
- Ablation (Table 7 p.18; 3 runs): without LlamaREST-IPD −9.2/−6.2/−8.4 pp (method/branch/line); without server response −6.1/−4.4/−6.3; without parameter description −5.9/−1.4/−4.5; without LlamaREST-EX −3.7/−4.5/−3.0.

## Stated limitations (with location)
- Less effective on services "that provide minimal or poor server feedback", where time is spent analysing uninformative messages (§4.4 p.17).
- Smaller model struggles with "complex parameter constraints, particularly for region-specific formats" and domain-specific knowledge (FDIC); "scenarios where larger models can have an advantage" (§4.2 p.13).
- 2-bit quantization degrades on domain-specific services (Genome-Nexus, Spotify) (§4.3 p.15).
- Threats (§4.7 p.19): benchmark representativeness; dependence on Martin-Lopez/APIs-guru fine-tuning data; limited tool set; settings may be non-optimal; measurement scripts; tool dependency on ARAT-RL.

## Limitations we observe (labelled OURS)
- OURS: "Semantic validity" is judged by two developers on generated values, but no inter-rater statistic (kappa) is reported; the number of values judged per service is not stated.
- OURS: The paper does not measure how often type-conformant (syntactically valid) random values are rejected by the server — the trigger "repeated failures (multiple 4xx)" (§3.4 p.10) implies this happens but no rate is quantified.
- OURS: Internal numeric inconsistencies (22.94% vs 24.94%; 17 vs 18 IPDs) should be resolved against the ACM version before citing exact figures.
- OURS: No statistical tests or variance for the 10-run averages; "significantly" used informally.
- OURS: The RL loop and 1-hour budget conflate LM quality with throughput — the paper itself attributes part of the quantization gain to faster inference (§4.3 p.15).
- OURS: Focused on test generation (finding 500s/coverage), not on validating incoming inputs at runtime.

## Future work stated
§6 p.20: "expand our approach's capabilities to handle a wide variety of API types and refine its dynamic interaction with server responses for even more effective test input generation."

## Relevance to our RQs (RQ1 structural-pass-but-semantic-fail; RQ2 frequency by field type; RQ3 LLM vs random/rule/human inputs; RQ4 violation types; RQ5 semantic layer detection; RQ6 latency/overhead; RQ7 trade-off)
- RQ1: Provides the clearest published definition and measurement of *semantic* validity of LLM-generated API inputs, separate from type conformance: a base 8B LLM produced semantically valid values only 22.94% of the time on average, 0% for Spotify (Table 3 p.12), while ARAT-RL's default values are already "in conformance with the expected types" (§3.4 p.10). This is direct evidence that type-valid ≠ semantically valid, though the paper does not report the pass rate of these values against actual server validation.
- RQ2: Per-service, not per-field-type breakdown (Table 3). Field-type examples given qualitatively: coordinate formats, ISO-8601 time, region codes (en-GB), 22-char Spotify IDs, OSM tag filter (§2.4 p.6; §4.2 p.13; §4.5 p.17).
- RQ3: Compares fine-tuned small LLM vs base LLM vs GPT-3.5-based RESTGPT for value generation (Table 3), and LLM-augmented testing vs random/type-based generators inside RESTler/EvoMaster/MoRest/ARAT-RL for coverage (Fig. 4, Table 6). No human-written input group.
- RQ4: Uses the Martin-Lopez IPD taxonomy (Requires, Or, OnlyOne, AllOrNone, ZeroOrOne, Arithmetic/Relational/Complex) (§3.2 p.7) — a ready-made taxonomy of cross-parameter semantic violations; plus format violations (§2.4 p.6).
- RQ5: The semantic layer here is on the *generation* side (fine-tuned LM produces semantically valid values, learns IPDs from server error text); it is not a validator of incoming inputs. Server 4xx messages act as the semantic oracle.
- RQ6: Gives concrete LM inference latency (26–49 s per IPD extraction on M1 MacBook Pro, §4.3 p.15) and model sizes (2.96–7.95 GB, §3.3.3 p.10) — useful reference points for overhead of an on-premise small-model semantic layer.
- RQ7: Explicit effectiveness–efficiency trade-off between quantization levels (§4.3 p.15; RQ2 summary box p.16): 2-bit loses accuracy on domain-specific APIs; 4/8-bit retain most accuracy with faster inference.

## Potential gap / novelty evidence (quote LOCATION, e.g. "§5.2 p.7: authors state X"; short quotes only, ≤ 25 words)
- §2.4 p.6: "Current state-of-the-art testing tools often generate invalid API requests, without considering the parameter value formats and the IPDs."
- §4.2 p.13: "a semantically valid input must be coherent with the API domain [2]. For instance, 'Berlin' is a valid input … whereas 'dog' is not." — an operational definition of semantic validity we can adopt/cite (primary source: ARTE [2], Alonso et al., TSE 2023).
- Table 3 p.12: base Llama3-8B 22.94% semantically valid on average; Spotify 0.00%, Ohsome 2.78%.
- §4.4 p.17: "LlamaRestTest may be less effective on services that provide minimal or poor server feedback" — the approach depends on the server already emitting informative semantic-error messages; it does not build that layer.
- §1 p.2: "the first black-box testing approach that leverages Language Models (LMs) to incorporate dynamic server feedback during REST API testing".
- Gap for us: no measurement of how often LLM inputs pass schema/type checks yet fail server-side semantic validation; no runtime semantic validator; overhead reported only for the tester's own LM inference.

## Terminology the paper uses for structural-vs-semantic validity (and how it defines a "valid" input)
- "Semantically valid" input / "semantically valid values" (§3.2 p.7; §4.2 p.13; Table 3 caption p.12): "a semantically valid input must be coherent with the API domain [2]" (§4.2 p.13); also "realistic parameter values" (§3.4 p.10; §6 p.20) and "valid, realistic parameter values".
- Structural side is expressed as "type/format specifications, constraints" (§2.2 p.5), values "in conformance with the expected types" (§3.4 p.10), and OAS keywords "minimum, maximum, pattern" (§1 p.2). The paper does not use the word "syntactic".
- "Inter-parameter dependencies (IPDs)": "relationships between API parameters where the value of one parameter affects another, ensuring valid and contextually appropriate parameter combinations" (§2.2 p.5).
- Operational validity signal at test time: HTTP status — 2xx success, 4xx client error, 500 server error (§2.1 p.4; §3.4 p.10); "valid inputs" in RQ1 are those judged domain-coherent by human raters, not those accepted by the server.
