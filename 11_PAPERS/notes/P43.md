## Problem
LLM-integrated applications (Bing Chat, Copilots, ChatGPT plugins) retrieve external data and call APIs; because LLM behaviour is modulated by natural-language prompts, "LLM-Integrated Applications blur the line between data and instructions" (Abstract p.1). Prior prompt-injection work assumed the *user* is the attacker prompting the model directly; this paper shows adversaries can *remotely* compromise applications by placing prompts in data that will later be retrieved and ingested (Abstract; §1 p.1–2). Fig. 1 p.1: "adversaries could control the LLM, without direct access, by indirectly injecting it with prompts placed within sources retrieved at inference time."

## Research question(s)
No numbered RQs. Stated contributions (§1 p.2): (1) introduce the concept of Indirect Prompt Injection (IPI), in which retrieved prompts "act as 'arbitrary code'"; (2) the first taxonomy and systematic analysis of the IPI threat landscape; (3) practical feasibility demonstrations on real-world (Bing Chat, GitHub Copilot) and synthetic (GPT-4 / text-davinci-003) systems; (4) public release of demonstrations and attack prompts.

## Method / architecture / algorithm
- **Threat model / taxonomy** (§3, Fig. 2 p.3, Fig. 3 p.3): attacker plants instructions in a source the LLM will retrieve; when the user prompts, the model ingests them; if the model has tools/APIs it can communicate back to the attacker or perform unwanted actions.
- **Injection methods** (§3.1 p.3–4): *Passive* (placed in public sources retrieved by search — websites, social-media posts, SEO-promoted pages, code repositories, personal documents via retrieval plugins); *Active* (delivered, e.g., e-mails to LLM-augmented mail clients); *User-driven injections* (tricking the user into copy-pasting attacker text into the prompt, or classic social engineering); *Hidden injections* (multi-stage payloads, images for multi-modal models, encoding such as Base64, prompts produced by Python programs the model is told to run).
- **Threat taxonomy** (§3.2 p.4–5, adapted from cyber threat taxonomies): Information Gathering, Fraud, Intrusion, Malware, Manipulated Content, Availability; targets can be untargeted or targeted (§3.2.1 p.5).
- **Experimental setup** (§4.1 p.5–6): synthetic chat-app built on OpenAI APIs (text-davinci-003 with LangChain + ReAct prompting, and gpt-4 with the chat format; Prompt 1 p.14, Prompt 2 p.15) with mock tools Search, View, Retrieve URL, Read/Send Email, Read Address Book, Memory; all interfaces return *prepared* content; sampling temperature 0. Real systems: Bing Chat (GPT-4) tested via the Microsoft Edge sidebar with injections hidden in local HTML comments (§4.1.2 p.6), and GitHub Copilot (§4.1.3 p.6).
- **Demonstrations** (§4.2–4.3 p.6–11; prompts/screenshots in Appendix A p.14–33): information gathering via side-channel URL (Prompt 3, Fig. 13); phishing (Prompt 4, Fig. 14); malware links (Prompts 5–6, Fig. 15); prompt-as-worm spreading via e-mail (Prompt 7, Output 1, Fig. 6); remote control via fetched instructions (Prompt 8, Output 2, Fig. 7); persistence via memory (Output 3, Fig. 8); code-completion contamination (Figs. 9, 16, 17); arbitrarily wrong summaries (Prompt 9, Fig. 18); biased output (Prompt 10, Fig. 19); source blocking (Prompt 11, Fig. 20); disinformation (Prompt 12, Fig. 21); undisclosed advertisement (Prompt 13, Fig. 22); availability attacks — time-consuming background tasks (Prompt 14), muting via <|endoftext|> (Prompt 15), inhibiting search (Prompt 16, Figs. 23–24), disrupting search queries with homoglyphs (Prompt 17, Fig. 25), disrupting results with zero-width joiners (Prompt 18, Fig. 26); multi-stage injection (Prompt 19, Output 4, Fig. 12); Base64-encoded injection (Prompt 20, Fig. 27); visual injection on LLaVA (Fig. 28 p.33).

## Stated limitations (with location)
- §5.2 "Experimental Setup" p.11: attacks tested on synthetic applications and local HTML files (Bing Chat sidebar) to avoid performing actual injections in the wild; could not test Microsoft 365 Copilot or ChatGPT plugins.
- §5.2 "Evaluation" p.11: no quantitative success rates — "quantifying our attacks' success rate can be challenging in the setup of dynamically evolving and interactive chat sessions"; left for future work; prompts written with grammatical errors on first draft to show low sophistication needed.
- §5.2 "Deception and Believability" p.11: qualitative only; the model sometimes produced "conspicuously false answers"; deception potential needs user studies.
- §5.4 p.12: exact reproducibility on Bing Chat is difficult (black-box, no control of generation parameters, dynamic environment).
- §5.6 p.12: authors could not integrate undisclosed real-world defenses into the synthetic apps.

## Limitations we observe (labelled OURS)
- OURS: The injection vector is retrieved *content* (web pages, e-mails, code, memory); the paper never considers structured application form fields with a declared type/schema, so the "structural pass" side of our RQ1 has no direct analogue here. The closest is Figure 17 (p.22): an injection in a Python docstring of a Flask app — a syntactically valid file whose semantics are malicious.
- OURS: No measurements at all — no success rate, no FPR/FNR, no latency; the paper cannot inform RQ6/RQ7 numerically.
- OURS: Mitigations (§5.6) are discussed but none is implemented or evaluated; no input-validation layer is proposed, only sketched ("processing the retrieved inputs to filter out instructions").
- OURS: All demonstrations use temperature 0 on a single provider (OpenAI) plus Bing Chat; generality across models is asserted, not shown.

## Future work stated
§5.2 p.11: quantify success rates and deception via user studies. §5.3 p.11–12: multi-modal injections and hiding methods; encoded/compressed injections; security of autonomous/multi-agent systems (lateral spreading, self-induced injections via reflection). §5.6 p.12: study RLHF vs. attacks, input filtering of retrieved data, LLM supervisor/moderator, interpretability-based outlier detection — and evaluate their robustness to obfuscation. §6 p.13: "urgently-needed security evaluation of LLM-integrated applications and future autonomous agents".

## Relevance to our RQs (RQ1 structural-pass-but-semantic-fail; RQ2 frequency by field type; RQ3 LLM vs random/rule/human inputs; RQ4 violation types; RQ5 semantic layer detection; RQ6 latency/overhead; RQ7 trade-off)
- **RQ1:** PARTIAL / conceptual. The core thesis — the model cannot separate "data" from "instructions" (§4.2 p.6; Key Message #1 p.3) — is the LLM-side statement of our claim that syntactically valid content can carry semantically harmful intent. Remark 2 (§4.2 p.6) documents that the chat-interface filter is bypassed when the same text arrives via a retrieved channel, i.e., a first-layer check passed while the semantic threat remained.
- **RQ2:** NONE. No field types, no frequencies.
- **RQ3:** NONE. Inputs are hand-written by the authors.
- **RQ4:** DIRECT as a taxonomy source. The six threat classes (Fig. 2 p.3) and four injection methods (§3.1) give a ready-made typology of semantic violations delivered through untrusted input; the "User-Driven Injections" class (§3.1 p.4) is the closest to user-typed form content.
- **RQ5:** PARTIAL. §5.6 p.12 discusses (but does not test) filtering retrieved inputs, an LLM moderator, and outlier detection; states the dilemma that a less-capable filter model may miss encoded input.
- **RQ6:** NONE. No overhead or latency is reported.
- **RQ7:** NONE quantitatively; §5.6 notes only that RLHF-based defense follows a "Whack-A-Mole" style and that "it is currently hard to imagine a foolproof solution".

## Potential gap / novelty evidence (quote LOCATION, e.g. "§5.2 p.7: authors state X"; short quotes only, ≤ 25 words)
- Key Message #1, §3 p.3: "Retrieval unlocks new doors for prompt injections where current (likely brittle) input filtering techniques are not applied in some of today's systems." — STATED; direct evidence that existing input filtering is described as brittle and channel-specific.
- §4.2 p.6: "prompts that are typically filtered out via the chat interface are not filtered out when injected indirectly" — STATED; input-side filters are applied inconsistently across channels.

- §5.6 p.12: Bing Chat "seems to employ additional filtering on the input-output channels without considering the model's external input" — STATED; validation layers exist but do not cover the retrieved-data channel.
- §5.6 p.12: "it is currently hard to imagine a foolproof solution for the adversarial prompting vulnerability" — STATED; open problem.
- §5.2 p.11: no quantitative evaluation of attack success — STATED limitation; a gap for measurement work.
- Fig. 17 p.22 / §4.2.4 p.8: injection carried inside a well-formed source file's docstring — OUR INFERENCE that this is a structural-pass/semantic-fail instance.

## Terminology the paper uses (how it names user-input-borne attacks/flaws vs. input validation)
- "Indirect Prompt Injection (IPI)" — attacker-placed prompts in retrieved data (Abstract; §1 p.2). Contrasted with "Prompt Injection (PI)" performed by a malicious user directly (§1 p.1; §3 p.3).
- Injections are described as "arbitrary code" (§1 p.2), "prompts as worms"/"AI malware" (§4.2.3 p.7), "poisoning the input data" (§3.1 p.4).
- Retrieved content is "untrusted retrieved data", "untrusted sources", "retrieved inputs" (§2 p.3; §5.6 p.12); the safety mechanism is called "input filtering techniques" (Key Message #1 p.3), "filtering on the input-output channels" (§5.6 p.12), "processing the retrieved inputs to filter out instructions" (§5.6 p.12). The phrase "input validation" does not appear.
- "User-Driven Injections" (§3.1 p.4) = injections delivered through what a user pastes or types.
- Threat classes: Information Gathering, Fraud, Intrusion, Malware, Manipulated Content, Availability (Fig. 2 p.3).
