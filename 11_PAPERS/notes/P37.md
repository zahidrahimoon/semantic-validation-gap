# P37 — wrenn2026enterprise
Verification level: V4 · Read depth: full · Read on: 2026-09-20 · PDF: 11_PAPERS/pdfs/2026_Wrenn_EnterpriseWorkflow.pdf
Bibliographic: Evaluating LLM Trade-offs for Enterprise Automation: Lessons from Workflow Generation in a Production Enterprise Platform; Xavier Wrenn, Radoslav Raykov, Aleksandar Angelov, Hirokuni Kitahara, Yuji Watanabe, Anca Sailer (all IBM); 2026; arXiv:2608.03311v1 [cs.SE] 4 Aug 2026; 10 pages, IEEE two-column format with Index Terms. No venue stated.

## Problem
Enterprise compliance management needs rapid, context-adapted remediation automation; static orchestrators fail in hybrid clouds (Abstract p.1). IBM Concert Workflows (CW) AI generates low-code JSON workflows from natural-language prompts (§I p.1). The primary metric, **structural success**, is "generation of workflows that conform to CW's JSON schema, pass validation checks, and render correctly in the UI" (§I p.1). The authors note "this metric does not assess whether workflows logically fulfill user intent, which we term semantic correctness. A workflow can be structurally sound while selecting incorrect action blocks or producing incomplete automation" (§I p.1).

## Research question(s)
No numbered RQs. Stated study aim (§I p.1): evaluate performance and accuracy of six LLMs for low-code workflow creation across two pipeline versions (monolithic v1 vs piecewise v2), tracking structural success, semantic correctness (§VI), latency, tokens, and cost per workflow. Hypothesis motivating v2 (§III p.2): decomposing generation into discrete sequential stages would reduce per-step complexity and let a broader range of models succeed.

## Method / architecture / algorithm
- v1 pipeline (§III.A pp.2–3): Classifier (intent, reject HAP/copyright, rewrite with IT terminology) → Reasoning (ReAct + RAG; tools: Block search, Workflow semantic search, Planner) → Generate workflow (single monolithic JSON) → Fact-checker (verifies block existence, schema validation using Zod, required metadata/variables, input types; errors mapped to JSON lines) → Generate JSON Patch feedback loop (default max 2 iterations).
- v2 pipeline (§III.B pp.3–4): Planner moved out of the reasoning loop and called deterministically early; added data sources (Chunked data, Human readables, user Documents); Update plan; generation decomposed into Generate workflow variables → Generate base blocks → Generate nested blocks; Attempt programmatic fix (low-cost fixes for escaping, malformed action blocks, simple syntax) before Generate JSON Patch.
- Post-hoc schema validation with iterative JSON Patch correction, contrasted with grammar-constrained decoding (§II p.2).
- Experimental setup (§IV.A pp.4–5): six models (Table I p.5): granite-4-h-small (32B, 9B active), llama-3-3-70b-instruct (70B), llama-4-maverick-17b-128e-instruct-fp8 (400B, 17B active), mistral-small-3-1-24b-instruct-2503 (24B), mistral-medium-2505 (~70B), gpt-oss-120b (117B, 5.1B active); all 131,072 context; input price $0.00006–$0.003 and output $0.00025–$0.01 per 1K tokens. 29 real-world compliance IT automation prompts (AWS Security Groups, VPC/EC2, RHSA patching with Ansible, SevOne, Instana). 8 independent runs × 29 prompts × 6 models × 2 pipelines = 2,784 runs. vLLM inference stack for gpt-oss-120b held constant across versions.
- Semantic evaluation (§VI pp.6–8): external LLM judge, Anthropic Claude Sonnet 4.5 via IBM BOB Shell, temperature 0; rubric of three semantic criteria (completeness, action-block selection, logical correctness) + seven platform-convention criteria (naming, descriptions, credential handling, etc.); outputs a 0–100 composite score and a binary "prompt satisfied" verdict. 348 cells (2 × 6 × 29) × 3 gradings = 1,044 gradings; verdicts reported as majority vote of three gradings. Only structurally valid workflows graded; selected from the 8 runs by a corruption-detection size threshold (≥40% of the largest valid run), lowest-numbered three.

## Dataset(s) (+ size, licence) / benchmark
29 real-world compliance IT automation prompts "based on actual user requests to the CW AI system" (§IV.A p.4); full prompt list stated to be in "the project repository" (§IV.A p.5) — no URL given. Licence: Not reported. Proprietary IBM Concert Workflows platform, action-block catalogue, and retrieval indexes are not public.

## Baselines
No external baselines. Comparisons are v1 (monolithic) vs v2 (piecewise) pipelines across the same six models (§IV.A p.5). Judge independent of all six model families to avoid self-favoring bias (§VI.A p.6).

## Metrics
(§IV.A p.5) Duration (request → validated workflow); token consumption (input/output); cost (tokens × published pricing); workflow generation rate (any workflow produced vs rejection/pipeline failure); **structural success** (JSON validity, schema compliance, UI renderability). (§VI pp.6–8) Semantic accuracy: mean composite score (0–100) with standard error across 29 prompts; majority-vote prompt-satisfaction %. Annualised cost projection at 1,000 workflows/day (§V p.5).

## Key results (each with table/figure/page reference)
- Table II p.6 (v1, 232 runs/model): structural success — granite 31.5%, mistral-small 33.2%, mistral-medium 39.2%, gpt-oss-120b 82.8%, llama-3-3-70b 53.0%, llama-4-maverick 57.8%; avg time 18.54–99.28 s; avg cost $0.0029–$0.0745.
- Table III p.6 (v2): structural success — granite 84.1%, mistral-small 95.7%, mistral-medium 96.1%, gpt-oss-120b 97.8%, llama-3-3-70b 74.1%, llama-4-maverick 90.5%; avg time 33.57–151.39 s; avg cost $0.0080–$0.1969; avg input tokens 61,487–117,594.
- Table IV p.6 (v1→v2 deltas): structural success +52.6, +62.5, +56.9, +15.0, +21.1, +32.7 pts; time +10.78, +8.26, +15.72, −33.06, +75.24, +15.03 s; cost +$0.0048 to +$0.1224. §V p.5: "No model in this 8-run evaluation reaches 100% structural success"; v2 latency rises 8–75 s for most models (Fig. 2 p.7: approx. linear input-tokens vs time).
- §V p.5 annualised cost at 1,000 workflows/day: mistral-small ≈ $3,700/yr; llama-4-maverick ≈ $8,900/yr; gpt-oss-120b ≈ $6,000/yr; mistral-medium ≈ $71,900/yr. Fig. 1 p.6: four v2 models in the ">90% success, <60 s" quadrant vs zero in v1.
- Table V p.8 (semantic accuracy, mean (SE) / majority-vote satisfaction): llama-4-maverick v1 59.8 (2.3) 27.6% → v2 71.5 (2.3) 55.2% (+11.7); mistral-small 46.6 (4.6) 17.2% → 66.4 (2.5) 34.5% (+19.8); llama-3-3-70b 57.2 (2.0) 6.9% → 63.6 (3.3) 34.5% (+6.4); mistral-medium 49.9 (4.2) 27.6% → 61.5 (4.3) 44.8% (+11.6); granite 57.3 (4.0) 27.6% → 58.8 (2.4) 17.2% (+1.5); gpt-oss-120b 58.9 (2.9) 24.1% → 44.9 (2.1) 6.9% (−14.0).
- §VI.C p.7: "Even the strongest model, however, failed the majority-vote satisfaction test on nearly half of the prompts, indicating that the high structural success rates reported earlier should not be interpreted as semantic correctness."
- §VI.D p.8 (second finding): gpt-oss-120b, best on structural metrics (97.8%), was worst semantically on v2 because it "frequently produced 'stub' workflows consisting of a single comment block declaring that the required actions were unavailable" — "These stubs pass structural validation but are non-executable."
- §VI.D p.8 (third finding): no model reliable; best majority-vote satisfaction 55.2%; "human review of generated workflows before execution remains necessary."
- §VII pp.8–9 per-model recommendations, e.g. llama-4-maverick "Strongly recommended for production"; gpt-oss-120b "Not recommended for production on v2 … despite leading structural metrics"; mistral-medium 19× cost of mistral-small for +0.4 pt structural gain (§VII.E p.9).

## Stated limitations (with location)
§IV.B p.5: rates are point estimates over 8 runs; per-cell CIs and significance tests "not yet computed and are left to future work"; structural success "measures JSON schema validity and UI renderability only — semantic correctness is addressed separately in Section VI but not yet integrated into the pipeline as a blocking validation step"; stub failure mode "suggests a model-specific sensitivity to the v2 prompt structure that warrants targeted follow-up". §VI.B p.7: only structurally valid workflows graded. §IX p.9: judge verdicts not yet validated against human ground truth; benchmark limited to the compliance domain.

## Limitations we observe (labelled OURS)
- OURS: Proprietary platform (IBM Concert Workflows) — schemas, action-block catalogue, retrieval corpora, and the "project repository" with prompts are not linked in the PDF, so the study is not independently reproducible.
- OURS: Semantic correctness is judged solely by an LLM judge (Claude Sonnet 4.5) with no human validation; the authors acknowledge this (§IX p.9). Judge rubric criteria are listed but the full rubric text is not in the paper.
- OURS: Semantic evaluation covers only 3 of 8 runs per cell and only structurally valid workflows; semantic error rates conditional on structural validity are therefore on a selected subsample.
- OURS: The stub failure (§VI.D p.8) is described qualitatively; its frequency per model/prompt is not tabulated, so the size of the structural-pass/semantic-fail population cannot be computed from the paper.
- OURS: Latency is end-to-end pipeline latency (retrieval + multiple LLM calls); the overhead of the Fact-checker / Zod validation / JSON Patch loop itself is not isolated.
- OURS: No breakdown of structural failures by type (schema violation vs. invalid block reference vs. type mismatch) despite the Fact-checker producing line-level diagnostics (§III.A p.3).
- OURS: Preprint; authors are the platform's developers (potential positive framing of v2).

## Future work stated
§IX p.9: (1) gold-standard benchmark with expert-annotated correct workflows per prompt to validate judge verdicts against human ground truth; (2) evaluating the judge as a post-generation validation step inside the pipeline giving iterative feedback to the generator (also §VI.D p.8: "trading additional token cost for improved semantic quality. We leave this design direction to future work"); (3) per-cell variance characterisation, confidence intervals, significance tests, prompt-complexity vs variance; (4) extend prompt coverage to Security, Networking, Compute, DevOps, Observability, Resilience, Risk domains; (5) regular model re-evaluation cadence. §IV.B p.5: targeted follow-up on gpt-oss-120b stub sensitivity; §VII.F p.9: prompt engineering to discourage stub generation.

## Relevance to our RQs (RQ1 structural-pass-but-semantic-fail; RQ2 frequency by field type; RQ3 LLM vs random/rule/human inputs; RQ4 violation types; RQ5 semantic layer detection; RQ6 latency/overhead; RQ7 trade-off)
- RQ1: DIRECT (production setting). Structural success up to 97.8% (Table III p.6) while majority-vote semantic satisfaction ≤ 55.2% (Table V p.8); gpt-oss-120b stub workflows "pass structural validation but are non-executable" (§VI.D p.8).
- RQ2: NONE. No per-field or per-field-type breakdown of either structural or semantic failures.
- RQ3: NONE. Only LLM outputs; no random/rule-based/human input comparison.
- RQ4: PARTIAL. Qualitative types: incorrect action blocks, incomplete automation (§I p.1), malformed JSON / incorrect block references / type mismatches for v1 (§III p.2), stub workflows (§VI.D p.8); no frequency table.
- RQ5: PARTIAL. LLM-as-judge with a 10-criterion rubric serves as an offline semantic layer (§VI pp.6–8); not deployed as a blocking check; judge accuracy vs humans unmeasured.
- RQ6: PARTIAL. End-to-end latency per model/pipeline (Tables II–IV p.6; 18.5–151.4 s) and token/cost figures; interactive threshold stated as <50–60 s (Abstract p.1, §V p.5); no isolated overhead of the validation layer; adding a judge step is anticipated to add token cost (§VI.D p.8) but not measured.
- RQ7: DIRECT for cost/latency vs structural success (Fig. 1 p.6, Table IV p.6, annualised cost §V p.5; mistral-medium 19× cost premium §VII.E p.9); semantic-vs-cost trade-off only qualitative.

## Terminology the paper uses for structural-vs-semantic validity
"structural success" / "structural validity" / "structural soundness" / "structural correctness" (JSON validity, schema compliance, UI renderability) vs "semantic correctness" / "semantic accuracy" ("logical fulfillment of user intent", Abstract p.1); "schema compliance as a proxy for correctness" (§VIII p.9); "schema-valid but non-executable stub workflows" (§VIII p.9); "prompt satisfied" verdict (§VI.A p.7); "production-viability threshold" (>90% structural success, §V p.5); "functional (structural) correctness" vs "semantic correctness" attributed to HumanEval (§II p.2); Index Terms include "structural validation" (p.1).
