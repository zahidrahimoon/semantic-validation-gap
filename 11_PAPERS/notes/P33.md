# P33 — li2026orderbench
Verification level: V4 · Read depth: full · Read on: 2026-09-20 · PDF: 11_PAPERS/pdfs/2026_Li_OrderBench.pdf
Bibliographic: When JSON Is Not Enough: Semantic Reliability of Schema-Constrained LLM Ordering Agents; Yin Li (University of Birmingham); 2026 (dated "May 2026" on p.1; arXiv stamp reads "arXiv:2607.18261v1 [cs.AI] 16 May 2026"); arXiv preprint, 7 pages, single author. No venue stated.

## Problem
LLM agents act as "transaction compilers": user states intent in natural language, model emits a structured object an API executes (Abstract, p.1). JSON Schema and provider structured-output modes remove parse failures but "do not by themselves decide whether the object is a safe, faithful transaction" (Abstract, p.1). The practical failure mode is "well-formed JSON that says the wrong thing" (§1 p.1). Existing structured-generation work uses a success criterion that "is usually structural: can the output be parsed, and does it match the declared type-level shape?" (§1 p.1). The paper studies "the next layer: semantic executability under a domain contract" (§1 p.1).

## Research question(s)
No explicitly numbered RQs. Implicit question (§1 p.1, §2 p.2): given that structured generation makes output schema-valid, "what remains unsolved after the structure is valid?" — i.e., how often is schema-valid output semantically wrong or unsafe to execute, and does provider JSON-schema mode change that relative to prompt-only JSON?

## Method / architecture / algorithm
- Benchmark design (§3 p.2): a restaurant menu with seven SKUs, item sizes, default modifiers, allowed additions/removals, allergens, dietary tags. Each example = customer utterance + deterministic oracle object with five top-level fields: `status`, `items`, `constraints`, `clarification_question`, `reasons`. `status` ∈ {accepted, needs_clarification, rejected_safety}. Schema forbids additional properties and bounds quantities to executable integers.
- 300 examples evenly across ten categories (§3 p.2): simple exact orders, quantity and size, negated modifiers, scoped modifiers, shared modifiers, allergen-safe acceptances, allergen conflicts, dietary conflicts, unavailable items, unavailable modifiers. Utterances are deterministic paraphrases of hand-written templates; "no model is used to create labels" (§3 p.2).
- Verifier (contribution list p.2): reports JSON validity, schema validity, status correctness, exact item semantics, constraint preservation, semantic success, unsafe acceptance.
- Two modes, same prompt (§4 pp.2–3): **Prompt-only** (prompt asks for JSON only, schema included as text) vs **JSON schema** (same prompt plus provider strict `json_schema` response formatting).
- Runs: all 300 cases, temperature zero, via Nebius Token Factory OpenAI-compatible API (§4 p.2). Raw responses, provider usage, latency, parsed objects, verifier results written to JSONL (§4 p.3).
- Statistics (§4 p.3): schema-minus-prompt rate difference, paired bootstrap 95% CI over cases, exact McNemar test on discordant paired outcomes.
- Proposed deployment architecture (§6 p.6, four steps): (1) strict structured output for parse/shape failures; (2) validate object against business catalog and safety policy; (3) fail closed on verifier errors, clarification rather than auto-repair for safety-critical fields; (4) log model output and verifier decisions as paired artifacts for regression testing.

## Dataset(s) (+ size, licence) / benchmark
OrderBench: 300 synthetic cases, 10 categories × 30 (Table 2 shows n=120 per category per mode, i.e. 30 cases × 4 models), seven-SKU menu (§3 p.2). Total calls: 2,400 (Abstract p.1) = 300 cases × 4 models × 2 modes. Licence: Not reported.

## Baselines
No external method baselines. The comparison is between the two output modes (prompt-only vs JSON-schema) for the same four models (§4 p.2): GPT-OSS 120B-fast, Qwen3-30B-A3B, Llama-3.1-8B, Gemma-2-2B. A fifth candidate was excluded by a compatibility pass because it "frequently exhausted the response budget and failed parsing" (§4 p.3).

## Metrics
(§4 p.3, Table 1 p.4) JSON validity; Schema validity; Status correctness; **Semantic success** (main metric: for accepted orders, correct status + exact multiset equality over SKU/quantity/size/additions/removals/special instructions + exact preservation of allergens and dietary constraints; for non-accepted orders, correct status, empty items, exact constraints); **Unsafe acceptance** ("most important risk metric": `status=accepted` for an object the verifier says must not be executed — allergen conflict, dietary conflict, unavailable item, unavailable modifier, or accepted item conflicting with a stated allergen). Multi-label error taxonomy: safety failures, catalog hallucinations, quantity/size errors, scope split errors, negation errors, allergen-preservation errors (§4 p.3, Table 3 p.5).

## Key results (each with table/figure/page reference)
- Table 1 p.4 (main results, %): GPT-OSS-120b-fast: JSON 100 / Schema 100 in both modes; Semantic 81.3 (json_schema) vs 83.0 (prompt_only); Unsafe 0.0 vs 0.3. Qwen3-30B-A3B: Schema 100 both; Semantic 30.7 vs 31.3; Unsafe 14.3 vs 15.0. Llama-3.1-8B: Schema 100 (json_schema) vs 68.7 (prompt_only); Semantic 36.0 vs 31.7; Unsafe 8.3 vs 13.3. Gemma-2-2B: json_schema Schema 100, Semantic 2.0, Unsafe 41.7; prompt_only JSON 99.7, Schema 91.7, Semantic 0.0, Unsafe 45.0.
- §5 p.3: "JSON and schema validity are much easier than semantic reliability. Structured mode often improves schema validity for smaller models, but it does not guarantee better business decisions or safer executable objects."
- Table 2 p.4 (category-level, aggregated across models): the hard categories are "domain boundary tasks: item availability, modifier availability, and user constraints that must change the execution status" (p.4). Unsafe rates highest for bad-item (51.7 json_schema / 58.3 prompt), bad-modifier (40.8 / 48.3), allergen-conflict (35.8 / 36.7), dietary-conflict (25.8 / 27.5); 0.0 for negation, qty/size, scope, shared, simple.
- Table 3 p.5 (multi-label error taxonomy, % of all 1,200 cases per mode): json_schema — Unsafe 16.1, Catalog 16.2, Qty/size 5.4, Scope 8.1, Negation 6.7, Allergen 4.7; prompt_only — 18.4, 17.2, 6.8, 7.5, 7.3, 4.8.
- Table 4 p.5: five representative schema-valid failures (e.g., "No dairy for me, add cheese sauce to fries" → Qwen3 (schema) accepts fries with cheese sauce → unsafe allergen; "Classic burger with pineapple" → accepts pineapple as add-on → catalog hallucination).
- Table 5 p.5 (paired JSON-schema minus prompt-only): GPT-OSS semantic Δ −1.7 [−5.0, +1.7], p=0.458; Qwen semantic Δ −0.7, p=0.804; Llama semantic Δ +4.3 [−0.7, +9.3], p=0.117 (not significant); Llama unsafe Δ −5.0 [−8.0, −2.0], p=0.001; Gemma semantic Δ +2.0 [+0.7, +3.7], p=0.031; Gemma unsafe Δ −3.3 [−6.0, −1.0], p=0.013. Text p.5: JSON-schema mode "significantly reduces unsafe acceptance for Gemma and Llama-3.1-8B, but does not eliminate the risk."
- Appendix A Table 6 p.7 (model × category heatmap): low scope score "is not solely a Gemma artifact: Qwen and Llama also struggle with split-item semantics, while GPT-OSS is substantially stronger" (p.6).

## Stated limitations (with location)
§7 p.6: benchmark is synthetic and single-turn; menu intentionally small, so rates "should not be read as deployment estimates for a particular vendor or restaurant"; evaluates one prompt and one provider interface; prompt engineering, fine-tuning, retrieval over a larger catalog, or a planner–verifier loop could improve absolute performance. "The central claim is narrower: schema validity alone is not a sufficient reliability metric for transactional execution."

## Limitations we observe (labelled OURS)
- OURS: Single-author preprint; no peer review stated; no code/data URL in the PDF despite "released JSONL outputs" (§4 p.3).
- OURS: Latency is recorded in JSONL (§4 p.3) but never reported or analysed — no overhead figures for the schema mode or for a verifier layer.
- OURS: The verifier (the "semantic layer") is hand-coded for a 7-SKU menu; no discussion of how the domain verifier generalises or of its own error rate.
- OURS: Only open models via one provider; no proprietary-model comparison; temperature 0 only, one run per case (no seed variation), though paired bootstrap CIs are given.
- OURS: "Semantic success" is exact-match on the whole object, so a single trivial miss (e.g., default size omitted) counts as failure; the paper acknowledges this (§4 p.3) but this inflates semantic-failure rates relative to a field-level view.
- OURS: Domain is restaurant ordering, not web-form / application input; the "fields" are order objects rather than typed form fields, so per-field-type frequency (our RQ2) is not directly derivable.

## Future work stated
No dedicated future-work section. §7 p.6 lists approaches that "could improve absolute performance" (prompt engineering, fine-tuning, retrieval over a larger catalog, specialized planner-verifier loop) without committing to them. §6 p.6 proposes the four-layer contract-stack architecture as a practical recommendation.

## Relevance to our RQs (RQ1 structural-pass-but-semantic-fail; RQ2 frequency by field type; RQ3 LLM vs random/rule/human inputs; RQ4 violation types; RQ5 semantic layer detection; RQ6 latency/overhead; RQ7 trade-off)
- RQ1: DIRECT. The entire paper quantifies structural-pass/semantic-fail: 100% schema validity with 2.0–81.3% semantic success (Table 1 p.4).
- RQ2: PARTIAL. Frequency broken down by task category (Table 2 p.4) and error type (Table 3 p.5), not by typed field (string/int/date/enum). Catalog hallucination (invalid enum-like value) and quantity/size errors are the closest analogues.
- RQ3: NONE for random/rule/human inputs; only LLM outputs are evaluated. It does compare prompt-only vs provider-constrained decoding.
- RQ4: DIRECT for a domain-specific taxonomy: unsafe acceptance, catalog hallucination, quantity/size, scope split, negation, allergen preservation (§4 p.3, Table 3 p.5).
- RQ5: PARTIAL. A hand-coded domain verifier is the detection layer and is advocated in §6 p.6, but its own detection performance is not evaluated (it is the oracle).
- RQ6: NONE reported (latency logged, not analysed).
- RQ7: PARTIAL. Table 5 p.5 shows schema mode reduces unsafe acceptance for weak models without improving semantic success significantly — a validity/semantics trade-off observation, not a cost trade-off.

## Potential gap / novelty evidence (quote LOCATION, e.g. "§5.2 p.7: authors state X"; short quotes only, ≤ 25 words)
- Abstract p.1: "structured output is a necessary interface layer, not a substitute for domain verification and fail-closed execution."
- §1 p.1: "The practical failure mode is therefore not only malformed JSON. It is well-formed JSON that says the wrong thing."
- §1 p.1: success criterion of structured-generation work "is usually structural: can the output be parsed, and does it match the declared type-level shape?"
- §2 p.2: "Our work assumes that structured generation is useful and asks what remains unsolved after the structure is valid."
- §6 p.6: "A JSON Schema can ensure that items is an array and quantity is an integer. It cannot ensure that a requested allergen conflict was rejected"
- §7 p.6: limitations confirm single domain, single-turn, no web-application/form setting, no latency analysis — leaves open our web-app field-level and overhead questions.
- §8 p.6: "production agents need semantic contracts, not only syntactic contracts."

## Terminology the paper uses for structural-vs-semantic validity
"syntactic validity" / "JSON validity" (parseable), "schema validity" (matches declared shape), "structural" success criterion, "type-level shape" (§1 p.1); versus "semantic reliability", "semantic executability under a domain contract" (§1 p.1), "semantic success" (exact domain-contract success, Table 1 caption p.4), "unsafe acceptance", "domain verifier", "semantic contracts" vs "syntactic contracts" (§8 p.6), "contract stack" (§6 p.6), "verified domain action" (§8 p.6).
