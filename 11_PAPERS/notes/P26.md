## Problem
Malformed, missing, or boundary-value inputs to microservice APIs can cascade across services. LLMs can generate robustness tests from API specs, but "it is unknown whether different models and prompt strategies produce diverse failure sets or converge on the same failures" (Abstract, p.1). Prior LLM test-generation studies measure compilation/correctness/coverage, not diversity of failure modes discovered (Sec. I, p.1).

## Research question(s)
(Sec. I, p.2)
- RQ1 (Coverage): How does failure mode coverage vary across models and prompt strategies?
- RQ2 (Diversity): How diverse are the failure mode sets produced by different models under the same prompt strategy?
- RQ3 (Domain Knowledge): Does incorporating mutation taxonomy rules from robustness testing research into LLM prompts improve coverage without collapsing diversity?

## Method / architecture / algorithm
- Controlled experiment: 7 prompt strategies × 3 open-source LLMs × 2 SUTs = 42 configurations; 38 valid runs; 663 generated tests (Abstract; Table I, p.3; Sec. III-D, p.4). Each configuration executed once (Sec. III-B, p.3).
- Models (Sec. III-B, p.3): qwen3:14b, qwen2.5-coder:32b (code-specialised), llama3.1:70b, hosted locally via Ollama with default inference parameters.
- Prompt strategies (Sec. III-C, p.3; Table II, p.4): ZeroShot (API spec only); Structured (pre-built violation table mapping endpoints → mutations → expected outcomes, hand-built by authors); FewShot (3–4 worked examples); CoT; Self-Refine (draft → critique → rewrite); Guided (Vieira et al. 2007 mutation taxonomy by data type: string/numeric/list/structural, no examples); GuidedFewShot (Guided + CRASH classification + concrete examples distinguishing key-absent vs value-empty vs value-null).
- Pipeline (Sec. III-D, Fig. 1, p.4): prompt construction → LLM generates Java/JUnit 5 tests → output cleaning (runs failing to compile excluded) → execution against live Dockerised SUT → response classification.
- Oracle: any HTTP status ≥ 500 = robustness failure (CRASH "Abort" class) (Table I, p.3; Sec. III-D, p.4).
- Failure mode (FM) = unique (endpoint, parameter, mutation-type) triple triggering HTTP ≥ 500, defined post hoc from observed failures and verified against source code (Sec. IV, p.4–5).
- Diversity metric: average pairwise Jaccard similarity of binary FM-coverage vectors across models within a strategy; union coverage across models (Sec. III-E, p.4).

## Dataset(s) (+ size, licence) / benchmark
- SUTs (Sec. III-A, p.3): TeaStore (Java, 6 services, form-encoded HTTP, 9 FMs) and OpenTelemetry Astronomy Shop demo (polyglot, 27 services, JSON APIs + gRPC, 14 FMs). Both open-source; licences: Not reported.
- No external dataset; the 663 generated tests and coverage matrices are in an anonymous repository (footnote 1, p.5).

## Baselines
No external tool baseline. ZeroShot and Structured serve as the two baseline prompt strategies against which FewShot, CoT, Self-Refine, Guided and GuidedFewShot are compared (Sec. III-C, p.3).

## Metrics
- FM coverage: fraction of FMs triggered per run (best single-run) and union coverage across models per strategy (Sec. III-E, p.4).
- Within-model cross-prompt union coverage (Table VI, p.7).
- Average pairwise Jaccard similarity (Table VII, p.7). Authors note ≤3 pairwise values per strategy: "descriptive indicators rather than statistically significant estimates" (Sec. III-E, p.4).

## Key results (each with table/figure/page reference)
- No single run exceeds 57% FM coverage: best 5/9 (56%) TeaStore, 8/14 (57%) OTel (Table V, p.6; Finding 1, Table VIII, p.9).
- ZeroShot: "models generate syntactically valid inputs that do not exercise boundary conditions or structural mutations" — union 1/9 (11%) TeaStore, 5/14 (36%) OTel (Sec. V-A-1, p.6; Table V).
- Structured prompting collapses diversity: Jaccard = 1.00 on both SUTs (Table VII, p.7; Finding 3).
- Prompt variation yields roughly twice the FM-set diversity of model variation: within-model cross-prompt J = 0.16 (TeaStore) / 0.19 (OTel) vs cross-model same-prompt J = 0.34 / 0.36 (Sec. V-B, p.7; Finding 2).
- qwen2.5-coder:32b reaches 14/14 (100%) OTel FMs with three prompts (Structured + GuidedFewShot + ZeroShot), exceeding any multi-model single-strategy union (max 64%) (Table VI, p.7; Sec. V-A-3, p.6).
- Key-absent vs value-empty: given only the taxonomy rule "replace parameter value by null", all three models generated only value-empty mutations, never key-absent; GuidedFewShot's concrete examples add FM3 and FM6 (both key-absent) on TeaStore (Sec. V-C-1, p.7; Sec. VI-A, p.8; Finding 4).
- qwen2.5-coder:32b under Self-Refine triggered 0 FMs on both SUTs because it omitted the assertNoServerError() oracle (Sec. V-C-2, p.7; Finding 6); 0% → 56%/57% under GuidedFewShot (Finding 7).
- ZeroShot uniquely finds state-based FMs (TeaStore FM9 unauthenticated cart removal; OTel FM14 checkout with empty cart) — FM14 appears in only 2/18 OTel runs, both ZeroShot (Sec. V-A-2, p.6).
- Emergent security inputs (XSS payloads, control characters) generated without instruction; these "did not trigger robustness failures because the SUTs' input parsers rejected them" (Sec. VI-E, p.9; Finding 9).
- Higher test volume ≠ higher coverage: 60 tests → 8/14 vs 12 tests → 3/14 (Sec. V-C-3, p.7–8; Finding 8).

## Stated limitations (with location)
- OTel currency and shipping services return HTTP 504 for all inputs in the available Docker deployment, so checkout FM5–FM14 HTTP 500s may reflect cascade rather than the mutation; classified by intended mutation (Sec. IV-B, p.5; Sec. VII-A, p.9).
- FM definitions are post hoc, risking overfitting the FM set to the models studied (Sec. VII-A, p.9).
- Single execution per configuration; no intra-configuration variance measured; single-run findings are "observations rather than reliable characterizations" (Sec. VII-A, p.9–10).
- External validity: both SUTs e-commerce reference apps; only three open-source 14B–70B models; prompts designed by authors (Sec. VII-B, p.10).
- Construct validity: HTTP ≥ 500 oracle misses silent failures (incorrect results with HTTP 200) and hindering failures (Sec. VII-C, p.10). Jaccard treats all FMs equally; binary matrix ignores frequency (Sec. VII-C, p.10).

## Limitations we observe (labelled OURS)
- OURS: The oracle is purely status-code based; the study explicitly cannot see inputs that are accepted (HTTP 2xx) but semantically wrong — precisely the class our project targets. The paper acknowledges this only as "silent failures" (Sec. VII-C, p.10) without measuring them.
- OURS: Inputs are LLM-generated *tests*, not LLM-generated *form/API data*; the paper studies the model as an attacker/tester, not as a data producer feeding a validated endpoint.
- OURS: Mutation types are a mix of structural (key absent, empty string, non-numeric) and value-level (expired card year, invalid currency code, negative month) but the paper does not separate these two classes analytically.
- OURS: No latency/overhead measurements of any validation layer; no validation layer is proposed.

## Future work stated
(Sec. VIII, p.10) Evaluate proprietary and larger open-source models; non-e-commerce SUTs; multiple executions per configuration for variance and significance testing; resolve the OTel infrastructure limitation; automate FM definition from API specs and source code. Weighted (severity-aware) Jaccard variant (Sec. VII-C, p.10).

## Relevance to our RQs
- RQ1 (structural-pass-but-semantic-fail): PARTIAL/INDIRECT. The paper shows the inverse mechanism for generation: unguided LLMs produce "syntactically valid inputs that do not exercise boundary conditions" (Sec. V-A-1, p.6). Its oracle cannot detect structural-pass-semantic-fail inputs at all (Sec. VII-C, p.10), which is evidence that this class is unmeasured in LLM-driven robustness testing.
- RQ2 (frequency by field type): PARTIAL. Tables III–IV (p.5) enumerate FMs per field (id, productid, cc.number, cc.year, cc.month, email, userCurrency, address.street) and Table VI lists per-model blind spots; FM13 (negative card month) was hardest. Not analysed as a field-type frequency distribution.
- RQ3 (LLM vs random/rule/human inputs): PARTIAL. Compares LLM prompt strategies vs each other and vs a hand-built Structured table, not vs random or rule-based fuzzers (Sec. II, p.2 positions against RESTler/EvoMaster but does not run them).
- RQ4 (violation types): PARTIAL. Uses the Vieira et al. taxonomy (string/numeric/list/structural mutations) and the key-absent vs value-empty vs value-null distinction (Sec. III-C, p.3; Sec. VI-A, p.8).
- RQ5 (semantic layer detection): NONE. No detection layer.
- RQ6 (latency/overhead): NONE.
- RQ7 (trade-off): NONE.

## Potential gap / novelty evidence (quote LOCATION; short quotes only, ≤ 25 words)
- Sec. VII-C, p.10: "Silent failures (incorrect results with HTTP 200) and hindering failures (degraded performance) are not detected" — the status-code oracle is blind to semantically invalid-but-accepted inputs.
- Sec. V-A-1, p.6: "Without guidance, models generate syntactically valid inputs that do not exercise boundary conditions or structural mutations." — evidence LLM default output is structurally well-formed.
- Sec. VI-E, p.9: security payloads "did not trigger robustness failures because the SUTs' input parsers rejected them before reaching application logic" — parser-level (structural) validation catches injection-style strings, consistent with our premise that structural checks are strong and semantic checks are the open question.
- Sec. VI-A, p.8: "mutation rules written for human testers carry implicit assumptions about protocol-level implementation that LLMs do not share."

## Terminology the paper uses for structural-vs-semantic validity
- "malformed, missing, or boundary-value inputs" (Abstract, p.1); "robustness failure" / "server-side failure" (HTTP ≥ 500).
- Mutation classes: "string", "numeric", "list", "structural (field-absent, field-null, empty body)" (Sec. II, p.2, after Vieira et al.).
- "key-absent", "value-empty", "value-null" mutations (Sec. III-C, p.3; Sec. IV-A, p.5).
- "parameter-focused" / "field-level mutations" vs "state-based" / "state-level mutations" (Sec. V-A-2, p.6; Sec. VI-B, p.8).
- "syntactically valid inputs" (Sec. V-A-1, p.6); "Silent failures (incorrect results with HTTP 200)" (Sec. VII-C, p.10).
- The phrase "semantic validity" appears once, only when describing the TestForge benchmark ("compilation success, runtime behavior, semantic validity, and functional correctness", Sec. II, p.2); the paper does not use "semantic validation" for its own inputs (checked via text search of the extracted PDF).
