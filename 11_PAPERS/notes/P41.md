## Problem
LLMs integrated into web apps and browser agents amplify classical web vulnerabilities (XSS, CSRF, etc.) and add LLM-specific ones; prior surveys "predominantly analyze LLM vulnerabilities in isolation or focus strictly on standalone agent interactions" (Sec. 2, p.3–4) and treat the LLM "as the final attack destination rather than a conduit" (p.4). Existing security frameworks (OWASP, NIST AI RMF, ISO/IEC, CWE) "were primarily designed for deterministic and traditional cybersecurity risks" (Sec. 6, p.27).

## Research question(s)
(Sec. 1, p.3) RQ1: How and to what extent do LLM security risks amplify, transform, or re-enable traditional web vulnerabilities across the web application stack? RQ2: Are existing defenses and security standards sufficient to mitigate these LLM-mediated risks across client-side, server-side, pipeline, and ecosystem layers?

## Method / architecture / algorithm
- Multi-stage methodology (Fig. 2, p.5): (I) map the 2025 OWASP LLM Top 10 to a "Traditional Threat-Reference Architecture" (TRA_01–TRA_10) grounded in MITRE CWE entries (Sec. 3, p.5–6; Table 2, p.7); (II) SLR following Kitchenham (Sec. 4, p.8–9); (III) per-risk comparative analysis with subsections "TRA_xx", "Amplification by LLMs", "Current Mitigation Approaches", "Open Research Challenges" (Sec. 5).
- Proposed "LLM-aware monitoring–control framework" (Sec. 6, p.28–29; Fig. 4, p.29): couples the six NIST AI 800-4 post-deployment monitoring dimensions with five LLM-specific controls: (i) prompt-level integrity verification, (ii) semantic input validation mechanisms, (iii) output-to-action isolation controls, (iv) capability-constrained agent governance, (v) continuous behavioural monitoring. Layers: Input Layer (semantic input validation) → Prompt Layer → Model Layer → Output Layer → Agent Layer → System Layer.

## Dataset(s) (+ size, licence) / benchmark

## Key results (each with table/figure/page reference)
- Framework limitations table (Table 5, p.28): OWASP — "Limited treatment of adversarial natural-language and prompt-level manipulation" → required extension "Instruction-aware threat modeling and prompt-level validation"; NIST AI RMF → "Continuous AI monitoring, drift detection, and lifecycle adaptation"; ISO/IEC → "Adaptive, context-aware governance"; CWE → extension toward prompt injection, embedding leakage.
- Sec. 6, p.28: NIST AI RMF and ISO/IEC "lack semantic input validation, prompt–execution separation, output-to-action control, agent autonomy governance, and continuous post-deployment monitoring."
- What "semantic input validation" means in this paper (Sec. 6, p.28): "received user queries are first processed through a semantic input validation layer (Input Layer), which identifies potentially adversarial instructions." — i.e. detection of adversarial natural-language *instructions* in user queries, not validation of data-field values.
- Prompt-injection mitigations reviewed (Sec. 5.1.3, p.11): StruQ [18] structured prompting / input separation; spotlighting [60]; signed prompts [133]. Open challenge: "Existing defenses often rely on heuristic filtering, which can be bypassed".
- "input validation" elsewhere: Sec. 5.2.3, p.12 — "comprehensive input validation techniques and monitoring mechanisms to identify and filter out sensitive information [4]" (ref [4] = Ahmed, Wei, Al-Shaer 2024, SACMAT, "Prompting LLM to enforce and validate CIS critical security control" — not an empirical input-validation study). Sec. 5.5.3, p.17: output "validation and neutralization"; "Structured output generation ... JSON schemas, further reduces the risk of unsafe output interpretation."
- Sec. 7, p.30: LLM-mediated interactions "weaken data–instruction, trust, and execution boundaries".

## Limitations we observe (labelled OURS)
- OURS: The proposed framework (Sec. 6, Fig. 4) is conceptual; it is not implemented, evaluated, or attached to any latency, FPR, or detection figures.
- OURS: "Semantic input validation" is defined only by one sentence (p.28) and refers to adversarial-instruction detection; the survey does not distinguish syntactic/structural validation of data from semantic validity of data values, and no primary study on that distinction is cited in the sections read.
- OURS: The survey's citation for "input validation" ([4]) concerns CIS security-control enforcement, not empirical validation of LLM-generated form/API data; the sections read cite no empirical work measuring semantic-input-validation effectiveness.
- OURS: The SLR's RQs are security-framing (attacks/defences), so benign-but-semantically-wrong LLM outputs (data-quality failures) fall outside its inclusion criteria (Table 3, p.9).

## Future work stated
(Sec. 5.1.3, p.11) "robust mechanisms for separating data from instructions in natural language interfaces, reliable detection of adversarial prompts across diverse contexts, and secure architectural designs that constrain the autonomy of LLM-driven agents"; (Sec. 5.5.3, p.18) "secure architectural designs that enforce strict separation between natural language generation and executable system actions"; (Abstract) three unresolved challenges: adversarial natural-language instructions, autonomous agent security, post-deployment monitoring.
