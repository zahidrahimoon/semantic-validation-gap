## Problem
Existing prompt-safety guardrails (LLM-as-a-judge such as Llama Guard 2, SafeDecoding, cloud moderation APIs) add "about 250–900 ms to each request", too slow for real-time applications that "usually need to respond in less than 100 ms", and cloud APIs also raise privacy concerns by routing prompts to external endpoints (Abstract, p.1; Sec I, p.1). Embedding-based methods exist but "lack latency evaluation" and are not tested on encoded/structured adversarial prompts (Sec II, p.2). The paper frames a "latency–accuracy–privacy trilemma" (Sec I, p.1).

## Research question(s)
No numbered RQs. Contributions (Sec I, p.1–2): (1) a low-latency local guardrail that detects harmful/jailbreak prompts before they reach the LLM; (2) a unified "Reflex Efficiency Score" (RES) for recall-vs-latency; (3) systematic comparison of seven lightweight classifiers on one benchmark; (4) evidence that attack families occupy distinct probability regions, motivating attack-aware thresholds; (5) deployment guidelines.

## Method / architecture / algorithm
Pipeline (Fig. 1, Sec III, p.3): jailbreak-aware preprocessor → compact embedding model → lightweight binary classifier → threshold decision.
- **Preprocessing** (Sec III-A, p.3–4; Fig. 2): regex-based detection of Base64 substrings via a sliding 4-character window (Eq. 1), decoded and prefixed with a "DECODED" marker; GCG-style suffixes (repeated punctuation / bracketed noise) are detected but not removed; DrAttack-style phrases ("As a researcher", "For educational purposes") raise sensitivity flags that adjust downstream thresholds. Stated overhead "less than 0.1 ms per request" (Sec III-A, p.4).
- **Embedding** (Sec III-B, p.4): BAAI/bge-small-en-v1.5 sentence transformer, ~33M parameters, input prefixed with "query:", mean pooling (Eq. 2), L2-normalised 384-d vectors (Eq. 3), cosine similarity (Eq. 4). "The embedding stage is the primary source of computational cost in the pipeline" (p.4).
- **Classifiers** (Sec III-C, p.4–5; Table II p.5): Logistic Regression (saga, class_weight=balanced), Random Forest (500 trees), XGBoost (250 est., depth 4), LightGBM (500 est.), HistGradientBoosting (500 iter), AdaBoost (300 est.), KNN (k=5). Output harm probability p; block if p ≥ τ (Eq. 6); default τ = 0.25 chosen from validation (Sec III-C, p.5).
- **Latency-oriented design** (Sec III-D, p.5): local execution (no network), 33M-parameter encoder, classifier inference "microseconds to low milliseconds"; sketch of a horizontally scaled deployment with load balancer → N Reflex-Guard instances → LLM router (p.5, described, not evaluated).
- **Threshold analysis** (Sec IV-G, p.9–10): F1-maximising threshold sweep (Eq. 9); attack-specific thresholds recommended (Table IX, p.11): 0.25 for GCG/Base64/general, 0.03 for DrAttack; two-tier screening proposed (Sec V, p.11).

## Dataset(s) (+ size, licence) / benchmark
Own composite dataset, 30,568 prompts (Table III, p.6): AlpacaEval 15,000 benign; Anthropic Red-Team 13,000 harmful (training; undersampled from 160,583); JailbreakHub/DAN 968 (evaluation, after MinHash dedup at Jaccard 0.85 from 1,000); JailbreakBench 800 (100 instructions expanded ×8 by back-translation/synonyms); MultiJail Bengali 800 (315 oversampled by paraphrase). Train 26,000 (13,000/13,000); test 4,568 (2,568 harmful / 2,000 benign) (Sec IV-A, p.5–6). OOD attack sets: 60 GCG-suffix, 100 Base64-encoded, 60 DrAttack prompts (Table V, p.8). Five-fold stratified CV for training (Sec IV-A, p.5). Licence: Not reported.

## Baselines
Seven internal classifiers compared against each other. External baselines Llama Guard 2 (recall 95.20%, 255 ms) and SafeDecoding (93.10%, 723 ms) appear in Table VII (p.9) but are "reported baseline results from prior work rather than running all systems under the same hardware and software settings" (Sec V Limitations, p.11). Table I (p.3) is a qualitative feature comparison with Llama Guard 2, SafeDecoding, OpenAI Moderation API and an "Embedding-Only" method [28].

## Metrics
Accuracy, precision, recall, F1, ROC-AUC (Table IV); recall per OOD attack family at τ=0.25 and τ=0.03 (Table V); component latency (Fig. 8) and end-to-end latency mean/P50/P99 in ms (Table VI); RES = Recall×100 / log2(Latency+1) (Eq. 7, p.8) and tunable RESα (Eq. 8, p.9); KL divergence between attack-family probability distributions (Eq. 14, p.11); FPR reported once in prose (Sec V, p.11).

## Key results (each with table/figure/page reference)
**Hardware for all timings:** Google Colab, NVIDIA Tesla T4 16 GB VRAM, batch size 1; CPU experiments on dual-core Intel Xeon with 12 GB RAM (results of CPU runs are not reported anywhere); Python 3.10.12, scikit-learn 1.2.2, XGBoost 2.0.3, LightGBM 4.0.0, sentence-transformers 2.2.2, transformers 4.35.2, PyTorch 2.1.0; all seeds 42 (Sec IV-B, p.6). **Latency protocol:** 10 warm-up passes, then 100 randomly sampled test prompts, mean / median (P50) / P99 via Python's time counter (Sec IV-A/B, p.6; Sec IV-E, p.8).

Latency / throughput:
- Embedding (bge-small-en-v1.5) = 35.27 ms per request on T4, the "main latency floor" (Sec IV-E, p.8).
- Preprocessing < 0.1 ms per request (Sec III-A, p.4).
- Component-level latency (Sec IV-E, p.8; Fig. 8): LightGBM classifier inference 2.32 ms, total component latency 37.59 ms; Logistic Regression total 37.97 ms; HistGradientBoosting and XGBoost ≈45–46 ms (HGB stated as 44.67 ms in Sec V, p.11); AdaBoost 106.20 ms; Random Forest 166.94 ms.
- End-to-end latency over 100 prompts, mean / P50 / P99 in ms (Table VI, p.9): Logistic Regression 53.17 / 40.85 / 325.80; LightGBM 54.88 / 41.71 / 284.73; HistGradientBoosting 69.81 / 53.34 / 463.53; XGBoost 85.90 / 65.60 / 540.61; KNN 88.67 / 71.81 / 491.72; AdaBoost 116.93 / 99.52 / 355.44; Random Forest 193.97 / 181.53 / 422.88. End-to-end includes "data conversion, GPU scheduling jitter, and garbage collection" (Sec IV-E, p.8).
- RES table (Table VII, p.9), recall % / mean latency ms / RES: LR 94.73 / 48.92 / 16.79; HGB 95.89 / 52.87 / 16.67; XGB 94.32 / 56.85 / 16.11; LightGBM 95.76 / 65.24 / 15.83; KNN 85.97 / 71.45 / 13.91; AdaBoost 92.52 / 113.28 / 13.53; RF 95.18 / 179.67 / 12.70; Llama Guard 2 95.20 / 255.00 / 11.90; SafeDecoding 93.10 / 723.00 / 9.80. Best RES is 41% above Llama Guard 2 and 71% above SafeDecoding (Sec IV-F, p.9). HGB adds 3.95 ms over LR for +1.16 pp recall (p.9).
- Throughput: Not reported (only qualitative "high throughput" claims, Sec III-D p.5). Cost: Not reported.

Detection / FPR:
- In-distribution at τ=0.25 (Table IV, p.7), Acc / Prec / Rec / F1 / AUC: HGB 0.954/0.952/0.959/0.955/0.990; LightGBM 0.953/0.951/0.958/0.954/0.990; LR 0.940/0.936/0.947/0.942/0.984; XGB 0.940/0.940/0.943/0.941/0.985; RF 0.939/0.930/0.952/0.941/0.984; AdaBoost 0.925/0.928/0.925/0.927/0.977; KNN 0.912/0.963/0.860/0.908/0.969. CV F1 std < 0.01 for HGB/LightGBM (Sec IV-C, p.7).
- OOD (Table V, p.8; HGB classifier): GCG suffix 60 samples 100% recall at τ=0.25 and 0.03, mean prob 0.79; Base64 100 samples 100%/100%, mean 0.63 (without preprocessing recall drops to 7%, mean prob 0.09, Sec IV-D p.8); DrAttack 60 samples 0% at τ=0.25, 100% at τ=0.03, mean 0.05 (σ 0.008).
- Threshold sweep (Table VIII, p.10): DrAttack recall 100% at τ ≤ 0.03, 75% at 0.04, 58% at 0.05, 33% at 0.06, 0% at ≥ 0.07; "general recall" 99.2% (0.01) → 98.7% (0.03) → 96.5% (≥0.07) → 95.9% (0.25 default).
- **FPR on benign inputs:** on the 2,000 benign AlpacaEval test prompts the predicted harm probability has mean 0.0021, median 0.0003, 99th percentile 0.0087, maximum 0.027, so τ=0.03 yields zero false positives (Sec IV-G, p.10; classifier presumably HGB, not stated). Separately, "At the default threshold of 0.25, Logistic Regression produces a 5.4% false positive rate, or about 1 in 20 benign prompts" (Sec V "False Positive Analysis", p.11); precision > 0.93 for top models. Confidence-based routing of near-threshold cases to human review or a slower LLM judge is recommended (p.11).
- KL divergence values between attack distributions: Not reported numerically (Eq. 14 defined only, p.11).

## Stated limitations (with location)
Sec V "Limitations", p.11: balanced 30,568-prompt dataset may not represent production traffic; harmful training data mainly Anthropic Red-Team; only three OOD attack types (multi-turn, indirect prompt injection, paraphrase, translation attacks untested); mainly English (Bengali preliminary); black-box threat model only (no white-box attacker who knows the embedding model/classifier); baseline comparison uses reported numbers, not same-hardware runs. Sec V "Ethics", p.12: "does not claim universal robustness"; should be one layer in defence-in-depth. Sec II, p.2: multi-turn, indirect injection and multilingual evasion "outside this evaluation's scope".

## Limitations we observe (labelled OURS)
- OURS: Internal numeric inconsistencies: the abstract's "37.6 ms end-to-end latency" matches LightGBM's *component* latency (37.59 ms, Sec IV-E), whereas the paper's own end-to-end mean for LightGBM is 54.88 ms (Table VI); Table VII mean latencies (e.g., LR 48.92 ms) differ from Table VI (LR 53.17 ms) with no explanation; text says default-threshold general recall is 99.1% (Sec IV-G, p.10) while Table VIII lists 95.9%.
- OURS: P99 end-to-end latencies (285–541 ms) exceed the paper's own sub-100 ms requirement; the "sub-100 ms" claim holds only for mean/median.
- OURS: The zero-FPR claim at τ=0.03 (Sec IV-G) and the 5.4% FPR at τ=0.25 (Sec V) are not reconciled; they appear to refer to different classifiers (HGB vs LR) and the FPR–threshold relationship is never tabulated.
- OURS: Citation integrity concern: several references carry implausible sequential placeholder arXiv IDs ([4] 2403.12345, [5] 2402.12345, [6] 2404.12345, [7] 2401.12345) and [4] attributes DrAttack to Andriushchenko et al.; the running header and author-biography placeholders indicate an unfinished manuscript. Any claim we take from this paper should be treated with caution and cross-checked (flag for human review).
- OURS: Benign data is AlpacaEval instruction prompts only; no application-structured or web-form inputs, so FPR on realistic web request payloads is unknown.
- OURS: The task is harmful-content/jailbreak detection, not prompt-injection or semantic validity of business data; baseline latencies (255 ms / 723 ms) are quoted from other papers on unknown hardware.
- OURS: Single run per configuration for latency (100 prompts, one seed); no variance across runs reported for latency; CPU-only latency, which matters for web servers, is never reported despite the CPU environment being described.

## Relevance to our RQs
- **RQ5 (semantic-layer detection):** PARTIAL–HIGH relevance as a design template: a 33M-parameter sentence-embedding model plus a classical classifier is exactly the class of "semantic layer" we are considering, and the paper shows harmful vs benign prompts are linearly separable in BGE space (LR F1 0.942, Table IV). However the detected property is harmfulness/jailbreak, not the semantic validity of a web request field.
- **RQ6 (latency/overhead):** DIRECT evidence, with hardware: embedding floor 35.27 ms on a T4, component totals 37.6–46 ms for fast classifiers, end-to-end means 53–70 ms with P99 285–464 ms (Table VI). Gives us a concrete reference point and a warning that tail latency, not mean, is the binding constraint.
- **RQ7 (trade-off):** DIRECT: RES metric (Eq. 7) and Pareto plot (Fig. 9) quantify recall vs latency; threshold sweep (Table VIII) quantifies recall vs threshold; and the DrAttack case shows a single threshold cannot serve all attack families.
- **FPR on benign inputs:** 5.4% FPR for LR at the default τ=0.25 (Sec V, p.11) vs zero FPR at τ=0.03 for the 2,000 AlpacaEval prompts (Sec IV-G, p.10) — evidence that FPR depends strongly on calibration and on the benign distribution.

## Potential gap / novelty evidence (quote LOCATION; short quotes only)
- Sec II, p.2: existing embedding-based evaluations "lack latency benchmarking" — supports our claim that ML input filters are rarely evaluated for overhead.
- Sec II, p.2: "existing works rarely measure the trade-off between security and latency" — direct statement of the RQ7 gap in the jailbreak-guardrail setting.
- Sec I, p.1: "real-time applications, when the system usually needs to respond in less than 100 ms" — a latency budget we can cite (unsupported by a reference in the paper; treat as the authors' assumption).
- Sec V, p.11: production recommendation to route near-threshold cases to "human review or a slower LLM-based judge" — supports a tiered semantic-validation design.
- Absence evidence: no evaluation on structured/application inputs and no CPU latency numbers, although a CPU environment is described (Sec IV-B, p.6).

## Detector design details useful for our semantic-layer candidates
- Embedding model: BAAI/bge-small-en-v1.5, 384-d, ~33M params, "query:" prefix, mean pooling, L2-normalised (Sec III-B, p.4).
- Classifier type: scikit-learn/XGBoost/LightGBM heads on the raw 384-d vector; hyperparameters in Table II (p.5); default τ=0.25 from validation; 5-fold CV; seed 42.
- Model size and hardware: 33M-param encoder on Tesla T4 (16 GB), batch size 1; CPU config dual-core Xeon 12 GB (no CPU results).
- How latency was measured: 10 warm-up passes, 100 random prompts, Python time counter, report mean/P50/P99; component latency = preprocessing + embedding + classifier; end-to-end additionally includes conversion, GPU scheduling, GC (Sec IV-A/B p.6, IV-E p.8).
- Reusable ideas: report P99 not just mean; attack-family-specific thresholds; preprocessing decoders (Base64) before embedding; RES-style single-number trade-off metric (Eq. 7).
