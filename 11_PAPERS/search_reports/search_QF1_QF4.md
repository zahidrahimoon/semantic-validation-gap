## 3. TERMINOLOGY NOTES

- **"Syntactic validation" vs "semantic validation"** — the exact OWASP pair (Input Validation Cheat Sheet, fetched): syntactic = "enforce correct syntax of structured fields (e.g. SSN, date, currency symbol)"; semantic = "enforce correctness of their values in the specific business context (e.g. start date is before end date, price is within expected range)". The page uses "business context" but no further formal term. Note OWASP puts range checks under semantic; our project's definition puts range/enum under structural — this mismatch must be reconciled in GLOSSARY.md.
- **"Business logic data validation" / "logically valid" vs format** — OWASP WSTG (BUSL chapter; search snippet): data should be "logically valid", testers use "logically 'invalid' data" that "do[es] not fit the business logic" even when format is correct. WSTG identifier not confirmed by fetch (page 404 on all three URL variants tried).
- **Academic security literature does not say "semantic validation"** for this concept. It says: **"logic vulnerabilities" / "logic flaws"** (Felmetsger 2010, Pellegrino 2014, Antaeus 2026), **"business logic vulnerabilities (BLV)"** (Metin 2025, MIRABELLE 2026), **"parameter tampering"** (Bisht 2010/2011/2014 — client/server validation mismatch), **"state violation"** (appears in a snippet for logic-flaw test generation), **"mass assignment"** and **"excessive data exposure"** (API-level OWASP names used by Corradini 2023, Pan 2024), **"broken access control"/"access policy violation"** (BACFuzz, Sahin 2026).
- **"Inter-parameter dependencies"** (Martin-Lopez et al.) is the API-testing community's term for cross-field constraints that "current specification languages … like the OpenAPI Specification provide no support for" — the closest formal academic treatment of "beyond-schema" constraints.
- **"Semantic" is overloaded**: in Razzaq 2014 / Aljawarneh 2010 it means ontology/semantic-web reasoning; in Hatfield-Dodds 2021 ("semantics-aware fuzzers") it means schema-derived data semantics; in Cheng 2020 it means URL structure; in Raz/Koopman/Shaw 2002 it means invariant-based "semantic anomaly" in data values (closest to our usage). Only Hanna & Munro 2018 use "semantic-based user input validation" in our sense.
- **"Invariant" / "likely invariants" / "behavioural specification"** — the invariant-inference thread (Raz 2002, Felmetsger 2010; Pellegrino 2014 uses "behavioral patterns" from traces).
- No academic term found for "structurally valid but semantically wrong" as a single phrase; the WSTG phrase "logically invalid data" is the nearest fixed label.
