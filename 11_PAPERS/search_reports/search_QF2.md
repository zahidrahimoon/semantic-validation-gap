## 3. How these papers measure input validity, and baselines used

Syntactic vs semantic validity:
- Execution-based (semantic) validity is the dominant measure for web/API inputs: C1 uses "successfully-submitted rate" (form accepted by server); C2 uses coverage of form-submission states; C14 uses HTTP 2xx (valid) vs 4xx (invalid) response classes; C11 uses an execution-based MySQL validator plus WAF bypass; C12 uses browser-runtime behaviour of XSS payloads rather than string similarity; C5/C6/C16/C20 use code/operation coverage and 5xx errors as proxies for inputs passing validation deep enough to reach logic.
- Explicit syntactic/semantic separation: C17 reports "89% syntactically and semantically valid test scripts"; C7 separates syntax correctness from executability and field coverage; C23 separates JSON-schema validity (70% raw -> 94–98% enforced) from semantic drift; C1 qualitatively reports format failures (e.g., malformed emails) as a distinct failure class.
- Schema/constraint conformance: C4, C19, C18 evaluate whether LLM-extracted rules/constraints are correct (precision) and whether generated values respect inter-parameter dependencies; C23 measures schema validity directly.
- Realism/diversity: C5 frames its goal as "realistic" inputs mined from example values; C13 measures input diversity and failure-mode coverage across prompt strategies; C3 targets input diversity via LLM + data fakers.

Comparisons with random / rule-based / human baselines:
- vs random or dictionary-based fuzzers: C3 (vs QExplore RL/random inputs; +7.7–11.9% statement coverage), C5 (vs RESTler, MoRest, EvoMaster, ARAT-RL), C16 (vs EvoMaster search-based mutation), C20 (vs RESTler dictionary values), C21 (vs AFL++ byte-level mutation), C6/C14 (vs prior REST tools).
- vs human-written: C22 (agent-synthesized generators vs human-written generators; higher branch coverage on 4/7 benchmarks); C24 (96% vs 98% manual).
- vs other LLMs only (no non-LLM baseline): C1 (11 LLMs and prompt/HTML-pruning variants), C7 (vs GPT-4o), C13 (3 LLMs x 7 prompts), C10 (MLLM benchmark), C15.
- No paper found in this pass that directly and systematically compares LLM-generated web-form inputs against both random and rule-based (e.g., faker/regex-based) generators on a shared syntactic/semantic validity metric — C3 is the closest (LLM + faker vs RL/random), C1 the largest empirical study but LLM-only.

## 4. Saturation note
- Queries 13, 15, 16, 17 mostly returned already-seen papers (C1, C3, C5, C13); the web-form and REST-API families appear saturated for 2024–2026 with the Kim/Sinha/Orso (RESTGPT, LlamaRestTest, AutoRestTest), Kogler et al. (RESTifAI, RESTestBench), Le et al. (KSE/JSAI), and Li/Huang (TOSEM) clusters.
- Queries 8, 10, 11 (schema validity / realistic test data / syntactically-vs-semantically valid) yielded almost no testing-specific hits; they surface structured-output and code-generation literature instead, suggesting the "semantic validity of LLM-generated web inputs" framing is under-populated in the literature (or uses different terminology).
- Adversarial-input family (query 7) returned distinct 2026 preprints (C11, C12) not seen elsewhere; a second pass on "WAF bypass LLM payload" and "LLM injection payload validity" could add more.
- Not yet found by search (do NOT cite until found): a peer-reviewed paper explicitly comparing LLM vs random vs rule-based web-form inputs on schema-validation pass rate.
